# 3D 아바타 + 실시간 LLM + 음성/억양 클로닝 챗봇 타진

작성일: 2026-08-04

> **문서 사용 안내 / 2026-09 갱신.** 이 문서는 3D NPC의 (1) 대화 텍스트 생성, (2) 음성 정체성·prosody 생성, (3) corpus 기반 Global Englishes 스타일, (4) 동의·라이선스·오인 방지 요건을 분리해 판단한다. 현재 Singapore 실행 경로는 `ASR → system-prompt-conditioned LLM → Singapore-supported CosyVoice v3-plus → audio output`이며, 3D 아바타는 3주차 이후로 미룬다. 공개 음성 코퍼스는 특정 개인의 clone source가 아니라 voice-class·ELF 전략 학습 자료로만 검토한다.

> **중요 운영 전환 / 2026-09-14.** 현재 가장 중요한 미해결 이슈는 cascade의 end-to-end conversational latency다. DDR cascade는 `qwen3.6-27b → Singapore CosyVoice v3-plus`를 통제된 연구 baseline으로 보존하지만, 초기 교실 적용 몇 주는 Deepgram Voice Agent 또는 ElevenLabs Voice Agent 통합 경로를 사용한다. Voice Agent는 DDR Model 1–3의 비교 모델이 아니라 학생 interaction·turn-taking·실제 latency를 검증하는 별도 운영 경로다. 1–2초 응답은 현재 cascade에서 검증된 사실이 아니며, provider의 best-case latency 표를 프로젝트 실측값처럼 사용하지 않는다.

## 0.0.0 현재 교실 적용 경로와 통합 Voice Agent 대안

시간 제약상 초기 교실 적용은 직접 구현한 `Deepgram STT → Qwen → CosyVoice` cascade가 아니라 관리형 Voice Agent 통합본을 사용한다. 후보는 다음 두 가지다.

| 후보 | 용도 | 공식 경로 |
|---|---|---|
| **Deepgram Voice Agent** | Flux STT/turn detection + agent orchestration + streaming TTS의 빠른 교실 pilot | [Voice Agent latency report](https://developers.deepgram.com/docs/voice-agent-latency-report), [Flux quickstart](https://developers.deepgram.com/docs/flux/quickstart), [Voice Agent Playground](https://playground.deepgram.com/?endpoint=agent&language=en&speakModel=flux-sean-en&listenVersion=v2&listenModel=flux-general-en) |
| **ElevenLabs Voice Agent** | 대안적 managed conversational voice-agent 및 TTS WebSocket 비교 | [Realtime TTS WebSocket](https://elevenlabs.io/docs/eleven-api/guides/how-to/websockets/realtime-tts), [ElevenAgents WebSocket](https://elevenlabs.io/docs/eleven-agents/libraries/web-sockets) |

이 통합 경로의 장점은 STT, endpointing/turn detection, LLM streaming, TTS streaming, interruption과 session orchestration을 하나의 운영 세션으로 제공한다는 점이다. 단, provider가 보고하는 `total_latency`는 보통 user utterance end부터 first audio byte까지의 best-case 또는 특정 배포 조건의 값이므로, 교실에서는 실제 브라우저의 `user speech end → first audible audio`를 별도로 기록한다.

현재 조사한 최신 공개 근거는 다음과 같다.

- Deepgram 공식 latency report는 STT, LLM first-token, TTS first-audio를 분해해 `total_latency`를 기록한다: <https://developers.deepgram.com/docs/voice-agent-latency-report>
- Deepgram/NVIDIA 배포 보고는 특정 조건에서 P50 약 660ms, P90 약 979ms, P95 약 1.282초를 보고하지만 이는 현재 프로젝트의 보장값이 아니다: <https://deepgram.com/learn/voice-agents-deepgram-nvidia-nemotron>
- Deepgram은 Flux가 conversational end-of-turn detection을 제공한다고 설명한다: <https://developers.deepgram.com/docs/measuring-streaming-latency>
- 실제 Pipecat 사례에서는 Deepgram STT/TTS와 GPT-4o를 사용해도 2–5초 지연이 관찰되었고, 원인은 TTS 자체보다 aggregation/playback 호출 흐름일 수 있었다: <https://github.com/pipecat-ai/pipecat/issues/1694>
- LiveKit은 region placement, endpointing, LLM TTFT, TTS TTFB, tool round trip을 분해해 측정해야 한다고 설명한다: <https://livekit.com/blog/understand-and-improve-agent-latency>

따라서 통합 Voice Agent는 지연을 **많이 줄일 가능성이 있지만**, 300–800ms를 모든 환경에서 보장한다고 기록하지 않는다. 초기 교실 pilot의 현실적인 검증 범위는 first audible audio P50/P90, full response, interruption latency를 실제 브라우저에서 측정하는 것이다.

## 0.0.1 아바타 확장 단계와 3D 공간 NPC 설계

현재 Deepgram 교실 웹에 추가할 수 있는 가장 작은 시각 확장은 **상반신
2D/2.5D talking avatar**다. 정면 상반신의 중립 PNG/WebP 한 장을 사용하고,
Deepgram Voice Agent의 `audio_chunk`, `UserStartedSpeaking`,
`AgentStartedSpeaking`, `AgentAudioDone` 이벤트를 기존 frontend visual layer에
연결한다.

이 방식은 다음 두 구현으로 나뉜다.

| 구현 | 준비물 | 가능한 동작 | 한계 |
|---|---|---|---|
| hosted talking-avatar | 정면 상반신 이미지 1장, provider Agent/client 설정 | provider가 입술·눈·표정을 영상으로 생성 | provider WebRTC/API와 Deepgram audio를 결합해야 하며 지연·비용·vendor lock-in이 발생 |
| local web 2D/2.5D | 이미지 + optional mouth/eye layers | amplitude 기반 입 열림, blink, listening/speaking 상태, 간단한 표정 | 단일 이미지 하나만으로 자연스러운 phoneme lip-sync는 불가능 |

따라서 상반신 이미지 하나는 **D-ID와 같은 hosted image-avatar 서비스의 입력으로는
충분할 수 있지만**, 우리 frontend가 직접 얼굴과 입술을 조절하는 데에는 충분하지
않다. local prototype은 closed/open/smile mouth layer 또는 sprite와 Web Audio
amplitude 신호가 필요하다. 이 시각 layer는 Deepgram의 STT/LLM/TTS를 대체하지
않으며, 특정 국가·언어 사용자를 얼굴로 재현하거나 대표한다고 주장하지 않는다.

### 0.0.1.1 3D 문화 공간과 NPC 대화 확장

후속 단계에서는 단일 avatar page를 넘어, 방(room)으로 나뉜 3D Global Englishes
공간을 만들 수 있다. 각 방은 국가나 인종을 장식적으로 고정하는 공간이 아니라,
학생이 영어를 사용할 **상호문화적 상황과 활동 맥락**을 제공해야 한다. 예를 들면
캠퍼스 카페에서 주문·협업하기, 도서관에서 과제 계획을 협의하기, 국제 학생
센터에서 길을 묻고 설명하기, 프로젝트 스튜디오에서 역할을 조정하기와 같은
장면을 사용한다.

권장 runtime 구조는 다음과 같다.

```text
3D world client (Unity WebGL / Three.js / PlayCanvas)
  → room scene + NPC placement
  → proximity trigger (student enters NPC interaction radius)
  → small conversation panel or spatial voice UI
  → Deepgram Voice Agent session (one persona, one voice ID)
  → avatar state + viseme/blendshape + audio playback
  → Apps Script transcript/session log
```

NPC 근처에 들어가면 해당 `room_id`와 `npc_id`를 고정해 대화 panel을 열고,
대화를 종료하거나 범위를 벗어나면 session을 닫는다. 로그에는 최소한
`room_id`, `context_id`, `npc_id`, `persona_id`, `voice_id`, `session_id`,
`proximity_start_ts`, `proximity_end_ts`, interruption latency를 남겨야 한다.
방의 배경·소품·과제는 GE/ELF/EIL/GELT 수업 목표와 연결하고, 방 이름만으로
국가적 성격이나 영어 능력을 추론하게 만들지 않는다.

이미지 기반 hosted avatar는 빠른 상반신 prototype에 적합하지만, 여러 NPC가
동시에 존재하고 공간 안에서 이동·접근·대화하는 구조에는 rigged GLB/VRM 모델과
blendshape/viseme가 있는 WebGL 또는 Unity 경로가 더 적합하다. Unity는
다중 room, NPC state, spatial trigger, animation을 확장하기 좋지만 WebGL
빌드와 JavaScript bridge까지 필요하다. 현재 웹사이트에 붙이는 첫 3D proof of
concept은 Three.js/PlayCanvas로 한 방·한 NPC·한 대화 panel만 구현하고, Unity
전환은 여러 방과 다중 NPC가 필요해지는 시점으로 미룬다.

범위와 시간 판단은 다음과 같다.

| 단계 | 결과 | 현실적인 시간 |
|---|---|---:|
| 상반신 2D/2.5D | Kit/Kai 이미지, idle/listening/speaking, amplitude mouth | 약 2시간 prototype |
| Web 3D proof of concept | 한 방, rigged avatar 1개, proximity trigger, Deepgram panel | 1–2일 |
| Unity WebGL world | 여러 문화적 상호작용 방, NPC state, spatial UI, 다중 로그 | 수일–수주 |

3D embodiment가 추가되면 avatar의 표정·방 배경·NPC 위치가 학생의
상호작용에 영향을 주는 독립적인 시각 처치가 된다. 따라서 현재 Deepgram 음성
pilot과 3D 공간 연구를 같은 효과로 주장하지 않고, `audio-only`,
`2D/2.5D-avatar`, `3D-spatial-NPC` 배포 조건을 별도로 기록한다.

**공통 파이프라인:**

```text
Student mic → Deepgram STT → Qwen 3.6 system prompt → CosyVoice v3-plus → audio playback
                                      ↓
                         Style Card + ELF strategy RAG
```

### 0.0.0 모델과 화자 AI의 분리 원칙

본 시스템은 **Model 1·Model 2·Model 3을 서로 다른 연구 모델**로 유지하되, 각 모델 안에서 여러 화자 AI를 선택하는 구조로 구현한다. 화자마다 별도의 챗봇 앱이나 별도의 LLM을 만들지 않는다.

```text
홈페이지
  → model_id 선택 (Model 1 / Model 2 / Model 3)
  → persona_id·voice_id 선택 (화자 AI)
  → 공통 대화 backend
  → 선택된 Style Card + reference audio + TTS 설정 적용
```

각 화자 AI는 `persona_id`, `voice_id`, 표시용 label, 승인된 Style Card, reference audio, consent scope를 가진 설정 레코드다. 따라서 홈페이지에는 화자 선택 화면을 두고, backend는 선택된 설정을 runtime에 주입한다. 음성만 다르다는 이유로 챗봇을 여러 개 복제하지 않는다.

Model별 구분은 다음과 같다.

| 구분 | Model 1 | Model 2 | Model 3 |
|---|---|---|---|
| 대화 모델 | Qwen 3.6 + system prompt/Style Card/RAG | Qwen 3.6 + system prompt/Style Card/RAG | Qwen 3.6 QLoRA + ELF data/RAG |
| 화자 선택 | 여러 `persona_id`/`voice_id` 선택 | 여러 `persona_id`/`voice_id` 선택 | 여러 `persona_id`/`voice_id` 선택 |
| 음성 처리 | reference-audio TTS | 화자별 TTS LoRA | 화자별 TTS LoRA |
| 앱 구조 | 하나의 Model 1 앱 | 하나의 Model 2 앱 | 하나의 Model 3 앱 |

실제 음성 파일의 source, 원본·파생 경로, 처리 이력, transcript, license, consent, TTS/chatbot/public 사용 허가와 reference clip 정보는 별도 운영 문서 `voices/voice-sources.md`에서 관리한다. 이 문서는 설계 설명용 요약이 아니라 실제 사용 음성의 권리·처리 provenance 기록이다.

### 0.0.0.1 Ollama 사용 범위

Ollama는 Model 1·2·3 중 특정 단계의 필수 구성요소가 아니다. 현재 기본 경로는 hosted/cloud Qwen endpoint이며, 이 경로에서는 Ollama를 설치하지 않는다.

- **Model 1:** Ollama 설치 없이 hosted/cloud Qwen endpoint로 실행한다.
- **Model 2:** Ollama 설치 없이 같은 Qwen endpoint를 사용하고, TTS LoRA inference는 cloud GPU 또는 hosted TTS endpoint에서 수행한다.
- **Model 3:** Ollama 설치 없이 QLoRA 학습·serving을 cloud GPU 또는 별도 model-serving endpoint에서 수행한다.
- **Ollama 선택 조건:** 로컬 Qwen 실행이 필요할 때만 설치한다. Ollama 설치 여부는 Model 1·2·3의 연구 조건이나 모델 차이를 의미하지 않는다.

특히 일반 PC에서 Qwen 35B를 Ollama로 실행하는 것을 기본 경로로 삼지 않는다. 로컬 Ollama는 개발용 smoke test 선택지이며, 연구 baseline의 필수 실행 환경이 아니다.

Model Studio를 hosted provider로 사용할 경우 `Qwen 3.6`은 문서상의 계열명이고, 실제 API에는 provider가 제시하는 정확한 model ID를 사용한다. DDR 연구의 active text base는 `qwen3.6-27b`로 고정하고, `qwen3.6-flash`는 active DDR Model 1–3에 섞지 않는다. Flash는 나중에 별도 latency benchmark가 필요할 때만 별도 조건으로 기록한다. OpenAI-compatible base URL·region·API key는 모두 같은 Model Studio region에 맞춘다. 공식 endpoint 문서: <https://www.alibabacloud.com/help/en/model-studio/compatibility-of-openai-with-dashscope>.

Model Studio에서 발급된 credential 정보에 `apiHost`, `openAiCompatible`, `dashScope`, `workspaceId`가 함께 표시되면 region을 사용자가 별도로 다시 선택할 필요가 없다. `ws-...ap-southeast-1.maas.aliyuncs.com`처럼 host에 region이 포함된다. 애플리케이션의 OpenAI SDK `base_url`에는 provider가 반환한 `openAiCompatible` 값을 우선 사용하고, `apiHost`·`dashScope`를 임의로 조합하지 않는다. `apiKey`는 source code·history·문서에 저장하지 않고 로컬 환경변수에서만 읽는다.

**Model 1의 Qwen 결정:** DDR cascade의 active text base는 Model Studio hosted `qwen3.6-27b`로 고정한다. 이 model은 Model Studio hosted API로 호출하므로 local Ollama가 필요하지 않다. `qwen3.6-flash`는 DDR Model 1–3 조건에 포함하지 않으며, 추후 별도 latency benchmark에서만 사용한다. `qwen3.6-27b`를 Model 3의 text SFT base로 유지해 Model 1과 Model 3의 base 차이를 만들지 않는다.

Model Studio에서 Qwen3.6-27B를 SFT 대상으로 선택하는 화면은 <https://modelstudio.console.alibabacloud.com/ap-southeast-1/model/tuning>이다. 이 화면의 `Qwen3.6-Open-Source` → `Qwen3.6-27B` snapshot 선택을 Model 3의 Alibaba managed SFT 진입점으로 기록한다. Model 1은 같은 base model의 hosted inference를 사용하고, Model 3은 승인된 text JSONL을 사용해 SFT를 별도로 실행한다.

개발 환경변수는 다음처럼 역할을 분리한다.

```text
DASHSCOPE_API_KEY  = Model Studio apiKey (secret)
QWEN_BASE_URL      = credential의 openAiCompatible 값
QWEN_MODEL         = qwen3.6-27b
DEEPGRAM_API_KEY   = Deepgram API key (secret)
```

#### Model Studio region 통일 결정

중국 본토 identity verification과 개인정보 제공을 요구하지 않는 Singapore 경로를 primary로 선택한다. Model 1은 Singapore Qwen3.6-27B와 Singapore에서 voice cloning이 지원되는 CosyVoice v3-plus를 사용한다.

```text
Singapore Model Studio
  ├─ Qwen3.6-27B text inference/SFT base
  └─ CosyVoice v3-plus voice cloning/TTS
```

따라서 `DASHSCOPE_API_KEY`, `QWEN_BASE_URL`, `DASHSCOPE_API_KEY_COSYVOICE`, `COSYVOICE_WS_URL`, `COSYVOICE_CLONE_URL`은 모두 Singapore workspace 기준으로 관리한다. Singapore API key는 새로 확인·교체해야 하며, Beijing key와 identity verification은 현재 프로젝트에서 사용하지 않는다. CosyVoice 2는 품질 우위가 확인된 대체 모델이 아니라 다른 region에서만 가능한 별도 모델 버전이므로 현재 계획에서 제외한다.

현재 PowerShell의 `$env:NAME` 설정은 해당 PowerShell과 그 자식 프로세스에서만 유효한 임시 설정이다. 프로젝트 앱이 시작될 때 자동으로 읽을 영구 개발 설정은 root의 `.env.local`로 관리하되, `.env.local`은 source control과 문서에 포함하지 않는다. `.env.local`이 자동으로 PowerShell 환경변수가 되는 것은 아니며, 앱의 dotenv loader가 읽도록 구현한다. 오늘의 API smoke test는 PowerShell 환경변수로 실행하고, 앱 연결 단계에서는 동일한 값을 `.env.local`로 옮긴다.

#### Annotation 선행 준비와 Model별 재사용

음성 자료의 annotation은 Model 2나 Model 3를 시작할 때 처음 하는 작업으로 미루지 않는다. Model 1 cascade 개발과 병행해 CHN_004의 master annotation을 먼저 만들고, 이후 모든 Model에서 동일한 source provenance와 annotation version을 재사용한다. 단, Model 1 시작을 전체 CA annotation 완료까지 지연하지 않으며, 먼저 최소 annotation으로 pipeline을 작동시킨다.

| 준비 단계 | 지금 준비할 내용 | 이후 사용 |
|---|---|---|
| Verbatim/transcript master | 단어·code-switch·filler·반복·false start·self-repair·speaker·turn timecode | Model 1 STT 검증, Model 2 TTS text, Model 3 SFT/RAG |
| CA·화용·대화 기능 | turn sequence, overlap/latching, repair, clarification, confirmation, reformulation, accommodation, topic shift, interaction function | Model 3 SFT/RAG text dataset |
| Acoustic/prosodic | pause duration, turn gap, speech rate/WPM, articulation rate, hesitation, emphasis, pitch/intensity/boundary 정보 | Model 1 평가, Model 2 TTS LoRA segment selection·평가 |
| Dataset split | train/dev/test 발화와 source·version·rights evidence 연결 | Model 2/3 학습·평가 누수 방지 |

Model 1에서 우선 완료할 최소 annotation은 speaker/turn/timecode, clean·overlap/exclusion 상태, matching transcript, 기본 pause와 WPM이다. Model 1 개발 중 전체 master annotation을 확장하고, Model 2 시작 전 acoustic annotation을 확정하며, Model 3 시작 전 CA·화용·대화 기능 annotation을 승인된 ChatML text dataset으로 변환한다. CA label이나 pause 숫자를 그대로 Qwen에 주입하지 않고, `system/user/assistant` 대화 예시와 필요한 metadata로 정제한다.

```text

voices/.../03_qc/ICNALE_SD_CHN_004_ca_annotation.csv
```

#### 연구용 cascade latency reduction plan

교실 적용 연구의 Deepgram Voice Agent 경로와 DDR의 cascade 연구 경로는 분리한다. DDR에서 latency를 줄일 때도 Model 1–3의 통제 가능성과 비교 가능성을 우선하며, classroom production의 1–2초 요구사항을 DDR cascade에 허위로 전가하지 않는다.

연구용 cascade에서 우선 검증할 순서는 다음과 같다.

1. **Metric 분리:** `user_turn_end → first_text_delta`, `user_turn_end → first_audio_chunk`, `response_end`를 분리 기록한다. full response latency만 줄이려 하지 않고 response onset을 primary latency로 둔다.
2. **Turn detection:** 현재 Nova `/v1/listen` endpointing baseline과 Deepgram Flux `/v2/listen` conversational turn detection을 별도 조건으로 비교한다. Flux 조건은 연구용 STT variant로 기록하며 classroom Voice Agent와 동일한 모델이라고 주장하지 않는다.
3. **Qwen 조건:** `qwen3.6-27b`를 quality-control baseline으로 유지하고, `qwen3.6-flash`를 low-latency ablation으로 별도 측정한다. 모델 ID가 달라지므로 두 결과를 같은 Model 1 품질 조건으로 합치지 않는다.
4. **Prompt/output bound:** source/rights mapping 전체를 realtime prompt에 넣지 않고 behavior와 delivery evidence만 사용한다. spoken reply는 1–2문장, 32–48단어, `max_tokens` 64–96 범위로 제한한다.
5. **Streaming overlap:** Qwen 전체 응답을 기다리지 않고 첫 complete clause를 CosyVoice에 넘긴다. 문장을 너무 잘게 쪼개 음질을 훼손하지 않도록 clause boundary와 minimum text threshold를 함께 기록한다.
6. **Connection/buffer:** Deepgram WebSocket과 Qwen HTTP connection을 재사용하고, TTS handshake/prewarm, browser audio queue depth, first MP3 frame 도착을 로그한다.
7. **Acceptance:** 동일 prompt/task의 반복 측정에서 first audio median/p95, full response, interruption stop latency를 함께 보고한다. 27B + CosyVoice v3-plus cascade에서 1–2초를 달성했다고 사전 가정하지 않는다.

현실적인 연구 목표는 현재 5–6초의 turn response를 **첫 음성 기준 2–4초 범위로 줄이는 것**이며, provider queue·region·endpointing에 따라 변한다. 일관된 1–2초가 필수인 교실 경로는 DDR cascade가 아니라 별도 Deepgram Voice Agent track에서 검증한다.

#### PNU 프로젝트로의 제한적 이전 계획

`2609_CA-GELT_Choe`의 Model 1은 Deepgram → Qwen → Singapore CosyVoice v3-plus cascade 개발이고, `2608_PNU`의 Model 1은 Gemini Live vanilla 조건이다. 두 프로젝트의 Model 번호와 기술 조건을 합치지 않는다. 2609의 산출물은 PNU의 Model 2·3을 개선하기 위한 **기술·분석 자산**으로만 이전한다.

| 2609 산출물 | PNU Model 2 | PNU Model 3 | 이전 경계 |
|---|---|---|---|
| cascade latency·turn log | broad prompt의 응답 길이·turn continuity 요구사항 참고 | calibration 변경 전후 latency/regression 확인 | PNU Live 조건에 cascade provider를 섞지 않음 |
| Style Card·persona registry | broad role/goal/voice label 설계 참고 | evidence-linked persona/context 변경 기록 | 실제 개인 voice clone은 PNU에 자동 이전하지 않음 |
| verbatim·acoustic annotation | broad 문제 pattern을 찾는 참고자료 | pause/WPM와 CA·화용 annotation을 selected rule/context로 변환 | raw audio보다 versioned derived annotation 우선 |
| prompt·평가 rubric | 전체적인 대화 지속·의미 우선 지침 | problem scene별 structured expert feedback | Model 2에 세부 CA 처방을 미리 주입하지 않음 |

PNU Model 2에는 2609의 상세 CA label이나 학생 transcript 기반 규칙을 직접 넣지 않고, 전문가가 Model 1을 사용한 뒤 합의한 broad guide만 반영한다. PNU Model 3에서는 Model 2 실제 learner–AI transcript를 CA 전사·화용 annotation하고, 관련 CA 문헌을 analytic lens로 사용한 뒤, 구조화된 전문가 피드백을 Change ID가 있는 rule/context/memory decision으로 변환한다. 이는 PNU 문서의 Model 2 broad expert customization과 Model 3 evidence-informed CA-mediated calibration을 유지한다.

두 프로젝트의 자료·코드·주장은 다음처럼 분리한다.

1. **공유 가능:** anonymized/versioned annotation schema, source provenance 필드, latency·turn log 필드, Style Card 개념, 검수 절차.
2. **조건부 공유:** CHN_004의 raw audio·transcript·reference clip. 두 프로젝트 모두에 대한 consent와 cloud/secondary-use 범위가 명시된 경우에만 source ID를 연결한다.
3. **공유하지 않음:** Deepgram/Qwen/CosyVoice 구현을 PNU Gemini Live 앱에 직접 병합, PNU learner memory를 2609로 이동, 한 프로젝트의 Model 1–3 결과를 다른 프로젝트의 동일 Model 효과로 주장하는 것.

실행 순서는 (a) 2609에서 CHN_004 Model 1 cascade와 master annotation을 완성하고, (b) annotation·provenance를 익명화한 transfer package로 고정하고, (c) PNU Model 2의 broad expert guide를 설계하며, (d) PNU Model 2 logs를 CA·화용 분석하고, (e) PNU Model 3의 evidence-linked expert calibration으로 변환하는 순서다. PNU의 실제 운영은 기존 Gemini Live·Apps Script·memory namespace를 그대로 유지한다.

#### 음성 자료 준비 원칙

모델 작동은 한 개 reference voice로 먼저 검증하지만, **자료 확보는 모든 계획 화자군에 대해 1주차부터 병렬로 진행한다.** 즉, 각 화자의 동의·녹음·전사·권리 확인을 먼저 완료하고, cloud pipeline 검증은 그중 품질이 가장 안정적인 baseline voice로 시작한다. 이렇게 해야 Model 2에서 화자별 TTS LoRA를 시작할 때 자료 수집을 다시 기다리지 않는다.

화자별 준비 패키지:

```text
speaker_<id>_reference.wav
speaker_<id>_reference.txt
speaker_<id>_consent.json
speaker_<id>_metadata.json
speaker_<id>_rights_check.md
```

Reference audio 기준:

- 영어 자연 발화 20–60초를 우선 확보한다.
- 한 명의 화자, 낮은 배경소음, 과도한 잔향 없는 파일을 사용한다.
- 원본 음성은 동의 범위와 연결해 별도 보관한다.
- reference audio의 정확한 transcript를 함께 보관한다.
- 개인 음성의 공개 코퍼스 사용은 별도 동의 없이는 하지 않는다.

#### Model 1–3의 STT/TTS provider 결정 (2026-09-13)

학생이 챗봇과 마이크로 자유롭게 대화하는 실제 운영 경로에서는 Model 1부터 Model 3까지 STT와 TTS가 모두 필요하다. 기존 CHN_004 전사본으로 오프라인 테스트를 할 때만 STT를 생략할 수 있다.

```text
학생 마이크 → Deepgram STT → Qwen 3.6 → Singapore CosyVoice v3-plus → 음성 재생
```

- **Deepgram**: 실시간 STT를 우선 provider로 확보한다. TTS(Aura/Flux)도 함께 확보하여 빠른 hosted TTS baseline과 latency 비교에 사용한다.
- **CosyVoice v3-plus (Singapore)**: 본 연구의 현재 canonical TTS 경로다. Model 1은 동의된 reference audio, Model 2–3은 여기에 화자별 TTS LoRA를 추가한다. CosyVoice 2는 현재 계획에 포함하지 않는다. v2가 v3-plus보다 우수하다고 판단할 근거도 확보하지 않았다. Deepgram TTS는 canonical TTS를 대체하는 것이 아니라 초기 baseline/비교 경로다.
- **Voice enrollment lifecycle**: 새 voice source마다 승인된 10–20초 reference audio로 CosyVoice v3-plus voice enrollment를 한 번 수행하고, 반환된 `voice_id`를 해당 persona profile에 저장한다. 실시간 turn마다 reference WAV를 다시 업로드하지 않는다. 다른 target model로 바꾸거나 voice를 재등록할 때만 별도의 `voice_id`가 필요하다.
- **Baseline fidelity boundary**: voice enrollment은 주로 timbre/voice identity와 일부 발음 특성을 복제하며, reference speaker의 실제 WPM, pause density, filler, hesitation, repair, learner-like fluency를 자동으로 재현하지 않는다. 현재 CHN_004 output의 높은 유창성과 빠른 속도는 Qwen이 정제된 문장을 생성하고 CosyVoice가 이를 자연스럽게 발화한 Model 1 baseline의 특성이지, 원본 학생의 말하기 행동을 충실히 복제한 결과가 아니다. 이후 speaker-specific TTS LoRA와 evidence-grounded delivery profile을 별도로 평가한다.
- **ElevenLabs**: TTS·voice cloning 품질 비교 후보이지 필수 provider가 아니다. 사용 시 별도 voice ID, consent, 외부 audio 전송 및 vendor terms를 확인한다.
- **Deepgram Voice Agent**: STT·turn taking·LLM·TTS를 한 플랫폼에서 연결한다. 이는 DDR Model 1–3의 연구 비교 경로가 아니라 초기 교실 적용의 managed production path다. DDR에서는 상업용 Voice Agent를 사용하지 않고 Qwen 3.6 + Style Card/RAG + CosyVoice reference audio와 후속 LoRA를 독립적으로 통제한다.

속도 조절은 가능하지만 layer를 구분한다. Qwen은 응답 길이·문장 경계·pause 지시를 제어하고, 실제 음성 속도는 TTS가 제어한다. Deepgram TTS는 session별 `speed`를 지원하며, ElevenLabs도 `voice_settings.speed`를 지원한다. Singapore CosyVoice v3-plus는 제공되는 TTS 설정과 실제 WPM, first-audio latency를 함께 기록하여 비교한다.

Qwen 3.6 Ollama library의 현재 태그(`27b`, `27b-mlx`, `35b`, `35b-mlx`)에는 cloud 태그가 없으므로, 이를 Ollama Cloud가 자동으로 실행한다고 가정하지 않는다. `qwen3.6:35b`를 유지할 경우 외부 Cloud GPU에 Ollama와 모델을 별도로 설치해 serving하거나, 해당 모델을 제공하는 별도 hosted endpoint를 사용한다. 로컬 PC의 Ollama 설치와 Qwen weight 설치는 개발용 선택 사항이며, 일반 PC에서 35B 실시간 inference의 필수 조건으로 두지 않는다. Fine-tuning은 Ollama가 아니라 외부 Cloud GPU의 QLoRA/PEFT 학습 환경에서 수행한다.

#### Alibaba Cloud Model Studio: inference API와 fine-tuning의 구분

Alibaba Cloud Model Studio는 단순 inference API만 제공하는 것이 아니다. 지원되는 Qwen base model에 대해 별도의 fine-tuning job을 API·CLI·console로 생성할 수 있고, 학습이 끝난 custom model을 dedicated service로 배포한 뒤 다시 hosted inference API로 호출할 수 있다. 즉 흐름은 다음과 같다.

```text
text JSONL 업로드
  → 별도 fine-tuning job (SFT/efficient SFT 등, model·region별 지원 여부 확인)
  → custom model 생성
  → dedicated deployment
  → custom model code로 inference API 호출
```

단순 chat completion API를 호출한다고 자동으로 fine-tuning되는 것은 아니다. 별도 학습 비용·권한·데이터 업로드·배포 단계가 필요하다.

- **Model 1:** Qwen hosted inference만 사용한다. Qwen fine-tuning은 하지 않는다.
- **Model 2:** Qwen은 Model 1과 같은 prompt/RAG 경로를 유지하고, 화자별 Singapore CosyVoice v3-plus TTS LoRA를 별도로 검토한다.
- **Model 3:** Qwen text-side fine-tuning을 검토한다. 1차 후보는 Alibaba Model Studio managed training이다. 선택한 정확한 model ID와 region이 원하는 SFT/efficient SFT를 지원하면 Model Studio에서 학습·배포하고 custom model API로 호출한다. 지원하지 않거나 QLoRA hyperparameter·replay buffer·adapter 관리에 대한 연구 통제가 필요하면 외부 cloud GPU의 PEFT/QLoRA를 사용한다.

현재 공식 Model Studio `model-training-overview` 표에서는 **Singapore의 `qwen3.6-27b`가 SFT Full Parameter Training과 SFT Efficient Training을 모두 지원**한다. 따라서 Model 1과 Model 3의 primary base를 `qwen3.6-27b`로 일치시키는 경로가 가능하다. 반면 `qwen3.6-flash`는 inference smoke test에는 사용할 수 있지만, SFT base로는 해당 Training 표에 등록된 지원 여부를 먼저 확인해야 한다. Model Studio의 model market 표시와 Training 지원표는 같은 의미가 아니므로 Training 표와 console의 실제 선택 가능 항목을 우선한다. 또한 Qwen fine-tuning에는 text JSONL만 업로드하며, 음성 reference audio 학습은 CosyVoice/TTS 단계의 별도 작업이다. source의 LLM training·third-party cloud processing 허가가 확인된 텍스트만 업로드한다.

공식 참조:

- Model Studio fine-tuning API/CLI: <https://www.alibabacloud.com/help/en/model-studio/fine-tuning-api-guide>
- Model Studio supported training models: <https://docs.modelstudio.console.alibabacloud.com/en/model-studio/model-training-overview>
- Model Studio Qwen OpenAI-compatible inference: <https://www.alibabacloud.com/help/en/model-studio/compatibility-of-openai-with-dashscope>
- Qwen3.6-Flash region/model support: <https://www.alibabacloud.com/help/en/model-studio/qwen3-6-flash>
- Custom model deployment: <https://www.alibabacloud.com/help/en/model-studio/model-deployment-quick-start>

현재 운영 결정은 연구·교실 경로를 분리한다. **DDR 연구는 Qwen text layer를 Alibaba Model Studio에서 관리하고 상업용 Voice Agent를 사용하지 않는다. 초기 교실 적용은 Deepgram Voice Agent 또는 ElevenLabs Voice Agent 통합본을 사용한다.** 여기서 `SFT`는 `Supervised Fine-Tuning`을 뜻하며, 승인된 ChatML text JSONL의 assistant 응답을 학습하는 text-side 방법이다. Model Studio는 DDR Qwen text inference와 text fine-tuning/deployment를 담당한다.

```text
학생 음성
  → Deepgram STT
  → Alibaba Model Studio Qwen text API
       ├─ Model 1: base model + system prompt/Style Card/RAG
       └─ Model 3: managed fine-tuned custom model API
  → Singapore CosyVoice v3-plus
  → audio playback
```

Model Studio의 fine-tuning method 이름과 우리 연구의 QLoRA를 자동으로 같은 것으로 기록하지 않는다. 콘솔에서 실제 선택한 model·region·training method·adapter/deployment plan을 확인하고, `efficient_sft`를 사용하면 그 이름을 그대로 기록한다. `QLoRA`가 연구상 반드시 필요하면 외부 PEFT/QLoRA 환경을 사용한다. CHN_004 transcript를 Model Studio에 업로드하는 것은 ICNALE의 LLM training·third-party cloud processing 권리가 확인된 뒤에만 허용한다.

## 1. 결론

가능하다. 현재 GitHub/Hugging Face/상용 API 생태계에 이미 필요한 구성요소가 존재한다.

목표 시스템은 다음과 같이 나눌 수 있다.

```text
3D 공간 / 3D 아바타
  + 실시간 LLM 대화
  + 음성 입력(STT)
  + 음성 출력(TTS)
  + voice cloning / accent cloning
  + lip-sync / facial animation
```

단, “목소리 복제”, “억양 복제”, “문법/말버릇 복제”는 서로 다른 문제다.

- 목소리 복제: TTS/voice cloning 문제
- 억양 복제: 해당 억양으로 말한 음성 데이터가 중요
- 문법 구조/말버릇 복제: LLM prompting, RAG, fine-tuning 문제
- 3D 아바타 동작: Unity/Unreal avatar, blendshape, animation, lip-sync 문제

가장 빠른 hosted 프로토타입은 **Unity 또는 Unreal + streaming LLM + hosted TTS + lip-sync** 조합이다. commercial TTS는 하나의 선택지일 뿐 필수는 아니며, Cloud TTS 또는 local open-source TTS를 쓰는 분리형 구현안은 §10을 따른다.

## 2. 실시간 LLM 연결 가능성

가능하다. 일반적인 구조는 다음과 같다.

```text
사용자 음성/텍스트
 → STT 또는 텍스트 입력
 → LLM streaming 응답
 → 문장/구 단위 chunking
 → TTS streaming
 → lip-sync / blendshape / facial animation
 → Unity / Unreal / Web avatar 출력
```

핵심은 LLM의 응답 전체를 기다리지 않고, token streaming 또는 sentence streaming으로 받아서 완성된 구/문장부터 TTS에 넘기는 것이다.

초기 설계상의 목표값(실측값이 아님):

| 구성 | 예상 체감 지연 |
|---|---:|
| 텍스트 입력 + LLM streaming TTFT | 약 0.3–1.5초 |
| 음성 입력 포함 first audio | 약 0.8–3초 (provider·turn detection 조건부) |
| TTS + 립싱크 포함 | 약 1.5–5초 (목표 범위, 보장값 아님) |

이 표는 provider, region, model, prompt 길이, endpointing, audio buffering을 고정한 실험 결과가 아니므로 Model 1의 acceptance criterion으로 사용하지 않는다. Model 1의 실제 hosted cascade는 별도 실측으로 판정한다.

## 3. Global Englishes voice & style cloning 가능성

가능하다. 단, 다음 세 요소를 분리해야 한다.

### 3.1 목소리 cloning

commercial TTS 같은 상용 서비스로 가능하다. 현재는 품질, 다국어, 감정 표현, API 안정성 면에서 상용 API가 가장 빠르다.


오픈소스/로컬 후보:

- English (US/UK/AU): CosyVoice, Qwen TTS 계열, XTTS-v2, OpenVoice, Chatterbox 계열
- Global Englishes (Singapore, Nigeria, Japan, Thailand L1 English): CosyVoice 2 cross-lingual + reference audio

### 3.2 억양/accent cloning

가능하지만, 좋은 결과를 위해서는 목표 억양으로 말한 음성 데이터가 필요하다.

예:

| 데이터 | 기대 결과 |
|---|---|
| L1 일본어 녹음만 있음 | 일본어 목소리 복제는 가능하나 Japanese-accented English는 불안정할 수 있음 |
| L1 일본어로 말한 English 녹음 있음 | Japanese L1 English 억양 복제 가능성 높음 |
| L1 태국어 녹음만 있음 | Thai voice는 가능하나 Thai-accented English는 불안정할 수 있음 |
| L1 태국어로 말한 English 녹음 있음 | Thai L1 English 억양 복제 가능성 높음 |

즉, "Japanese L1 English" 또는 "Thai L1 English"를 구현하려면 해당 화자가 실제로 영어를 그런 식으로 말하는 데이터가 가장 중요하다.

### 3.3 문법 구조·말버릇·code-switching cloning

"음성 클로닝"이라는 단어는 사실 4개의 독립 레이어로 분해되며, 본 절은 그중 텍스트 LLM이 책임지는 **L3 (lexis-syntax)** + **L4 (discourse-habit)** + **L2-text (prosody의 텍스트-인코딩 가능 부분)**을 다룬다. L1 (timbre)은 절 3.1의 TTS 모듈이, L2의 음향적 나머지는 절 3.2의 TTS prosody predictor가 책임진다.

| 레이어 | 예시 | 주체 모듈 | 본 절 범위 |
|---|---|---|---|
| L1 Timbre | 성대/성도 공명, 화자 고유 음색 | TTS (commercial TTS, F5-TTS, CosyVoice 2, XTTS v2) | 절 3.1 |
| L2 Prosody | pitch contour, F0 range, phrase break, duration | TTS prosody predictor + LLM prosody token (L2-text) | 절 3.2 / 절 3.3 일부 |
| **L3 Lexis-Syntax** | 선호 어휘, collocation, 통사 패턴, code-switching | **Text LLM (style card + few-shot + RAG)** | **본 절** |
| **L4 Discourse-Habit** | filler/disfluency markers, pause 위치, false start, repair, backchannel | **Text LLM (explicit token) + TTS (음성화)** | **본 절** |

#### 3.3.1 L3 Lexis-Syntax — 화자 어휘·통사·담화 마커

예 (Global Englishes code-switching):

```text
I think this one is a bit challenging, you know, because the concept is quite abstract.
```

**권장 구현 4단계 (가벼움 → 무거움):**

| 수준 | 방법 | 대표 논문/리소스 |
|---|---|---|
| 가벼움 | system prompt + few-shot examples (5–30 utterances) for a style probe, not high-fidelity speaker reproduction | Zhou et al. 2024, CharacterBench (arXiv:2412.11912) |
| 중간 | speaker/persona style guide (Style Card JSON) + RAG over spoken corpus | Salemi et al. 2024, LaMP (ACL 2024) / `0903 DDR_3D_GE.md` Model 3 |
| 무거움 | 실제 대화 데이터 기반 PEFT/LoRA fine-tuning, per-speaker adapter | Awesome-Personalized-LLMs (VanillaCreamer, 2026) — Aplaud/PLUME trend |
| 평가 | Per-speaker lexical/syntactic match metric, LongLaMP-style benchmark | Kumar et al. 2024, LongLaMP (arXiv:2407.11016) |

##### 3.3.1.1 Style Card schema artifact 및 검증

검증 가능한 예시는 [`test-card.json`](.research/test-card.json)에 보관하고, 구조 정의는 [`style-card.v1.schema.json`](.research/style-card.v1.schema.json)을 기준으로 한다. 빌더는 [`style-card-builder.py`](.research/style-card-builder.py)이며 `--validate` 옵션으로 schema를 검증한다. 1회 빌드 후 versioned artifact로 보관하며, 본 카드는 voice-class synthesis만 허용한다 (`safety.is_identity_clone: false`).
#### 3.3.2 L4 Discourse-Habit — 화자 발화 습관 (filler / pause / repair)

검토 가능한 방법: **LLM이 근거가 있는 경우에만 `[FILLER:well]`, `[PAUSE:0.4s]`, `[FALSE_START]`, `[REPAIR]` 같은 explicit token을 출력하고, TTS 단계에서 이를 음성화**한다. 그러나 few-shot만으로 원본 화자의 분포와 타이밍을 안정적으로 재현한다고 가정하지 않는다. Chaudhury et al. (2024)의 zero-shot filler 생성은 가능성의 근거이지 개인 화자 fidelity의 증명이 아니며, Matsunaga et al. (2022)의 filled-pause 연구도 실제 source annotation과 별도로 검증해야 한다.

| 레이어 | 대표 논문/리소스 | 핵심 발견 |
|---|---|---|
| L4 통합 모델 | Li et al. 2024, Spontaneous Style TTS (arXiv:2407.13509) | spontaneous behavior를 language model로 통합 모델링 |
| L4 zero-shot | Chaudhury et al. 2024, Humane Speech Synthesis (arXiv:2404.01339) | LLM이 zero-shot으로 filler·emotion 토큰 생성 |
| L4 실증 | Matsunaga et al. 2022 (arXiv:2210.07559) | filled pause personalization에는 position·word 동시 필요 |
| L4 keynote | Anumanchipalli 2025, SSDM (DiSS 2025) | articulatory gesture + CSA + LLM end-to-end |
| L4 transcript | Altinok 2025, Smooth Operators (DiSS 2025) | LLM이 timestamp cue만으로 disfluency-annotated transcript 생성 |
| L4 stutter | Lu 2026, DisSpeech (arXiv:2606.21457) | Mandarin stuttered speech synthesis for ASR augmentation |

**L4 explicit token notation (v1, draft):**

```text
[FILLER:well]   [PAUSE:300ms]   [FALSE_START:the, uh]   [REPAIR:sorry, I mean]
```

권장 아키텍처(절 4)의 LLM 출력은 plain text + L2 prosody token + L4 explicit token을 결합한 형태가 된다.

#### 3.3.3 L2-text — Prosody의 텍스트-인코딩 가능 부분

L2의 음향적 부분은 TTS가, 그중 다음은 LLM이 텍스트로 인코딩해 책임진다.

- clause boundary 위치 (의미 단위로 묶기)
- 강조 단어 (capitalization 또는 explicit `[STRESS]` token)
- emotion/prosody intent caption (Bagpiper-TTS 2026 패턴, arXiv:2606.22811)

**L2 LLM-side 방법:**

| 방법 | 대표 논문 | 비고 |
|---|---|---|
| Dynamic prosody token | Mou et al. 2026 (arXiv:2606.15267) | syllable-level prosody를 이전 음성에 조건부 예측 |
| Natural language caption | Tian et al. 2026, Bagpiper-TTS (arXiv:2606.22811) | LLM이 rich caption 생성 → TTS 입력 |
| Paralinguistic style | Lou et al. 2025, ParaStyleTTS (arXiv:2510.18308) | reference audio 없이 LLM prompt로 paralinguistic 제어 |
| Open-ended instruction | Zhang et al. 2026, Poly-InstructTTS (arXiv:2608.20387) | 1000+ fine-grained emotion/style을 instruction으로 학습 |
| Cascaded prompting | Ouyang et al. 2026 (arXiv:2604.08709) | textual style token + audio prompt + ICL online RL |

#### 3.3.4 L1 Timbre — 음색 레이어 참고

#### 3.3.11 실시간 latency + commercial TTS / F5-TTS / CosyVoice 2 비교

화자 동일성 4-레이어 보존을 실시간 대화에서 실현할 때의 latency 분해. 아래 값은 초기 설계 목표이며 현재 Singapore hosted cascade의 실측값이 아니다.

| 단계 | 기술 | 1st chunk 지연 | 출처 |
|---|---|---|---|
| STT | Deepgram Nova-2 / Whisper Realtime | 150–300ms target | 초기 설계값 |
| LLM TTFT | Qwen 3.6 streaming | 200–400ms target | 초기 설계값 |
| TTS 1st chunk | F5-TTS / CosyVoice 2 / commercial TTS Turbo | 150–500ms target | 초기 설계값 |
| **이론적 합산 목표** | | **500–1200ms** | 실측·보장값 아님 |
| Native Live (단일) | Qwen 3.6 text streaming | 350–600ms target | 초기 설계값 |

**TTS 옵션별 latency·기능 비교:**

| TTS | 1st chunk | 인프라 | L4 token | L2 prosody 통제 | 가격/라이선스 |
|---|---|---|---|---|---|
| commercial TTS Turbo v2.5 | **150–300ms** | cloud (WebSocket) | ❌ (SSML break만) | SSML emphasis 제한 | $5–22/월 (30k–100k chars) |
| F5-TTS (self-host) | 250–400ms | GPU 12–16GB | ❌ 직접 미지원 | reference audio에서 자동 | CC-BY-NC weight |
| CosyVoice 2 (self-host) | 200–300ms | GPU 8GB | △ instruction으로 부분 | **instruction-based style control** ✓ | Apache-2.0 |

→ commercial TTS는 latency 최소지만 L4·L2 정밀 통제 불가. 단순 음색만 복제하고 L4 disfluency는 LLM이 자연 텍스트로 출력하게 하면 commercial TTS로 충분.

#### 3.3.12 Text-side style fine-tuning 권고

**핵심 권고: L3·L4를 반복적으로 보존하려면 system-prompt-conditioned(§3.3.1)만으로 충분하다고 가정하지 말고, annotated text/CA data에 근거한 LoRA fine-tuning을 비교한다.**

System prompt와 few-shot은 빠른 탐색·스타일 가설 검증에는 유용하지만, 실제 화자의 문법 오류, filler 비율, hesitation, repair 분포를 고정밀로 복제하지 않는다. 규칙을 많이 넣을수록 지시 간 충돌, 과잉 적용, 문장 부자연스러움, turn 간 drift가 생길 수 있다. 따라서 “5–10개 예시로 fine-tuning과 대등하다”거나 “원본 학생의 구사력을 그대로 복제한다”고 주장하지 않는다. Model 1은 prompt/Style Card/RAG baseline으로 두고, Model 3은 source-grounded annotation과 held-out interaction test로 실제 개선 여부를 검증한다.

**Prompt vs Fine-tuning 정량 비교:**

| 차원 | Style Card + few-shot + RAG (prompt) | LoRA fine-tuning (QLoRA r=16) |
|---|---|---|
| TTFT | 200–400ms + JSON parse 10ms | 200–400ms (**동일**, LoRA forward +0–5ms) |
| Context 토큰 | Style Card 1–2KB + few-shot 500–2000B | 거의 0 (스타일 내재) |
| 일관성 | drift 가능; held-out test 필요 | 개선 가능하지만 데이터·학습 범위·held-out test로 검증 필요 |
| 업데이트 | 즉시 (JSON 수정) | 재학습 2–4h |
| 데이터 | 5–30 utterance | **300–5000 utterance** |
| 감사 가능성 | **높음** | 낮음 (style card로 부분 보완) |
| Per-speaker 분리 | style card swap | LoRA adapter swap (30–80MB/adapter) |

`qwen3.6-flash`는 이 프로젝트에서 low-latency ablation/운영 후보로 사용할 수 있지만, Model 3 SFT base와 동일하게 취급하지 않는다. Model 3의 fine-tuning 비교는 실제 console에서 training 지원이 확인된 `qwen3.6-27b` 조건을 기준으로 유지하고, Flash 결과는 별도 latency–quality 조건으로 보고한다.

**Global Englishes code-switching 가능 LLM (2026):**

| 모델 | 크기 | multilingual | code-switch | 라이선스 | 비고 |
|---|---|---|---|---|---|
| **Qwen 3.8** | 27B | ★★★★ | ★★★★ | **Apache-2.0** | **1순위, multimodal** |
| **Gemma 4** | 27B | ★★★★ | ★★★ | Gemma license | 비교 기록만 유지, 운영에서 제외 |

이 표는 후보군 평가 기록이다. **현재 10주 운영 경로에는 Qwen 3.6만 사용하고, Qwen 3.8은 9–10주차 비교용으로만 사용한다. Gemma 4는 비교 기록만 유지하고 운영 모델에서는 제외한다.**

**Fine-tuning 작업 (1 round, 1인):**

| 작업 | 시간 | GPU |
|---|---|---|
| 데이터 정제 + utterance 분리 + PII 제거 | 4–8h | none |
| LoRA r=16 (Qwen 3.6 27B) | **2–4h** | A100/H100 1장 |
| Hyperparameter 탐색 1 round | 2–4h | same |
| 평가 (predefined test set) | 2–4h | inference only |
| **합계** | **10–20h (1.5–3일)** | |

**데이터 요구량:**

- 50–100 utt: 약간 shift, overfit 위험
- **300–1,000 utt**: noticeable but rough, D-day 1차 작동에 적합
- 1,000–3,000 utt: high fidelity
- 5,000+ utt: production-quality

→ 본 프로젝트는 **300–1,000 utt (≈30–60분 자연 발화)**로 1차 작동 가능.

| 용도 | 소스 | 라이선스 |
|---|---|---|
| Per-speaker LoRA fine-tune | **자체 수집 (Class B 녹음)** | IRB 동의 필수 |
| Style Card RAG (general pattern) | ELFA/VOICE/ACE | restricted/open |
| L1-influenced code-switch | 자체 수집 + ELFA L1-influenced analysis | IRB |

**현재 운영 기준:**

1. **L4 disfluency를 LLM이 자연 텍스트로 출력** (fine-tune으로 internalize) → L4 explicit token notation 불필요
2. **Style Card는 metadata-only로 축소** (consent, source, IRB, build_recipe)
3. **TTS는 natural text → voice class 음성화** (F5-TTS / CosyVoice 2 / commercial TTS 모두 호환)
4. **Latency**: 600–900ms (cascade) — commercial TTS 사용 시 500–800ms

**Tradeoff 명시:**

- Fine-tuning audit 어려움 → style card의 `build_recipe.prompts_hash` + `human_reviewed` 필드로 부분 보완
- Per-speaker LoRA 관리 부담 → 30–80MB × 6화자군 = 0.5GB, 충분히 관리 가능
- Catastrophic forgetting → QLoRA + 1e-5 ~ 5e-5 LR + ELFA 1k utt replay buffer
- 초기 1차 작동: Model 1의 system-prompt-conditioned 방식으로 시작 → Model 2·3에서 순차적으로 TTS/LLM fine-tuning을 추가한다.

#### 3.3.14 Model 1–3 DDR 실행 경로

본 프로젝트는 **Model 1 → Model 2 → Model 3**으로 기록한다. 세 모델은 서로 다른 제품이 아니라 DDR 단계별 구현 상태다.

**Model 1 — 1–2주차: 음성 cascade baseline**

```text
Student mic → STT → Qwen 3.6 system prompt + Style Card/RAG → CosyVoice 2 → audio
```

- text LLM: Qwen 3.6, system-prompt-conditioned generation
- TTS: CosyVoice 2, 동의된 reference audio
- 목표: 음성 입력·텍스트 생성·음성 출력의 end-to-end 작동과 기본 화자 구별
- 3D avatar, camera, lip-sync는 포함하지 않음

**Model 2 — 3–4주차: 화자별 음색 강화**

```text
Student mic → STT → Qwen 3.6 system prompt + Style Card/RAG
           → per-speaker CosyVoice 2 TTS LoRA → audio
```

- text LLM은 Model 1과 동일하게 유지
- 화자별 TTS LoRA만 추가해 음색·prosody 개선 여부를 검증
- 비교 항목: speaker similarity, intelligibility, first-audio latency, artifact rate

**Model 3 — 5–8주차: 텍스트 화용 전략과 음성 통합**

```text
Student mic → STT → Qwen 3.6 QLoRA + ELF strategy RAG
           → per-speaker CosyVoice 2 TTS LoRA → audio
```

- text LLM: Qwen 3.6 QLoRA
- 학습자료: consented transcripts + VOICE/ACE/ELFA pragmatic-function annotations
- L5a 전략 패턴은 QLoRA로 학습하고, L5b는 system prompt/RAG로 통제
- L5c는 9–10주차 interaction test에서 별도 평가

**9–10주차 비교 실험:** Model 3의 Qwen 3.6 text model과 Qwen 3.8 text model을 동일한 TTS adapter, prompt, temperature, test set으로 비교한다. 비교 결과가 없으면 Qwen 3.8의 우월성을 주장하지 않는다.

**Cloud 운영:** Intel Arc 노트북은 데이터 준비와 client 역할만 수행한다. inference와 fine-tuning은 필요한 시간에만 cloud GPU를 임대한다. 별도 backup API와 24/7 GPU 임대는 운영안에서 제외한다.

#### 3.3.16 ELF 화용 전략 co-construction (L5: Interactional Competence) — fine-tuning 가능성

**핵심 질문:** "ELF 화자들이 화용 전략을 통해 local norm을 co-construction하면서 상호 이해에 이르는 과정"을 fine-tuning으로 재현할 수 있는가?

**Short answer: L5a (전략 패턴) = YES, L5b (전략적 competence) = PARTIAL, L5c (live co-construction) = LIMITED**

##### 3.3.16.1 L5 3-layer 분해

| Sub-layer | 정의 | Fine-tuning으로 재현 가능? | 구현 방법 |
|---|---|---|---|
| **L5a 전략 패턴** | clarification request, confirmation check, self-repair, collaborative completion, code-switching for pragmatic effect | **YES** (높음) | VOICE/ACE/ELFA 대화 transcript + function annotation으로 fine-tune |
| **L5b 전략적 competence** | "어떤 trouble source에서 어떤 전략을 언제 발동할지" 메타 의사결정 | **PARTIAL** | Fine-tune + system prompt + RAG (context-aware retrieval) |
| **L5c live co-construction** | interaction에서 emergent한 local norm 형성 (Kaur 2011, Pitzl 2016) | **LIMITED** | 시스템이 "tendency"를 가질 수 있으나, 동적 co-construction은 interaction 자체에서 발생 |

##### 3.3.16.2 핵심 ELF 연구 인용

- **Kaur, J. (2011)** "Doing 'being a professional' in a multilingual medical setting" — ELF 화자들이 화용 전략 (repetition, self-repair, collaborative completion)으로 local norm을 co-construction. TPRL framework.
- **Mauranen, A. (2012, 2018)** "Exploring ELF" — ELF는 native-speaker norm이 아니라 interaction에서 emerge하는 "lingua franca franca". AntConc 코퍼스 분석 방법론.
- **Pitzl, M.L. (2016)** "World Englishes, English as a Lingua Franca, and English as a Contact Language" — ELF의 non-understanding sequences가 어떻게 해결되는지 CA 분석.
- **Cogo, A. & Dewey, M. (2012)** "Analysing English as a Lingua Franca: A corpus-driven investigation" — efficiency vs. clarity, accommodation 전략.
- **Smit, U. (2010)** "English as a Lingua Franca in Higher Education" — AWE (Academic Writing ELF)에서 discourse-level 전략.
- **Klimpfinger, S. (2007)** "'Mind you' as a discourse marker" — ELF 화자의 discourse marker 사용 패턴.
- **Jenkins, J. (2000, 2007)** "World Englishes" — Kachru 3-circle 모델, Inner/Outer/Expanding circle.

##### 3.3.16.3 우리 적용: 4-layer (L1–L4) → 5-layer (L1–L5) 확장

| Layer | Fine-tuning 가능 | 우리 구현 |
|---|---|---|
| L1 Timbre | (TTS) | CosyVoice 2 reference audio |
| L2 Prosody | (TTS) | CosyVoice 2 instruction |
| L3 Lex-Syn | ✓ | Style Card v1 + QLoRA |
| L4 Discourse-Habit | ✓ | QLoRA |
| **L5a 전략 패턴** | **✓** | **QLoRA + VOICE/ACE/ELFA function-annotated dialog** |
| **L5b 전략 competence** | **△** | **System prompt + RAG (context-aware ELF strategy retrieval)** |
| **L5c live co-construction** | **✗ (system 한계)** | **Interaction design으로 보완** (prompt "be open to non-standard forms, negotiate meaning, use clarification") |

##### 3.3.16.4 L5a fine-tuning 데이터

**필수 corpus (인용 4개 모두 fine-tune data로 사용):**

- **VOICE (Vienna-Oxford International Corpus of English)** — 1M words, ELF 상호작용, 오픈 액세스
- **ACE (Asian Corpus of English)** — 1M words, Asian ELF
- **ELFA (English as a Lingua Franca in Academic Settings)** — restricted, 연구자 신청 필요
- **LINDSEI (Linguistics and Intercultural Studies Exchange)** — 대학생 ELF

**Annotation schema (L5a fine-tune data용):**

```text
{
  "turn_id": 42,
  "speaker": "S1",
  "L1": "Japanese",
  "utterance": "So, eh, photosynthesis is, you know, when plant makes food from sunlight?",
  "pragmatic_function": ["other_initiated_repair_attempt", "code_switch_for_explanation", "hedge_with_you_know"],
  "elf_strategy": ["simplification", "exemplification_with_question"],
  "trouble_source": "abstract_concept",
  "next_speaker_action": "confirmation_check"
}
```

##### 3.3.16.5 L5b RAG implementation (전략 competence 보완)

```text
System prompt (L5b layer):
"You are an ELF speaker in a multilingual academic setting. When you sense non-understanding or
abstract concepts: (1) prefer clarification requests over assumptions, (2) use code-switching
strategically for lexical gaps, (3) provide examples/reformulations, (4) signal understanding with
backchannels. Reference Kaur 2011, Cogo & Dewey 2012, Pitzl 2016."

RAG query: "{last_student_utterance} → retrieve: VOICE/ACE dialog with similar turn + pragmatic function tag"
```

##### 3.3.16.6 L5c interaction design (live co-construction 보완)

Fine-tuning으로 불가한 부분은 **interaction design으로 보완**:

- 학생의 L1 패턴을 prompt에 인식시킴 ("If learner hesitates or uses unfamiliar expressions, you may simplify or reformulate")
- 모르는 개념은 단순화 + 예시 + 확인 요청 3단계로
- "I mean", "you know", "I think" 같은 hedge를 자연스럽게 사용
- 학생이 hesitate하거나 unfamiliar expressions를 사용하면 simplify하거나 reformulate
- Repair initiator가 학생이 발화하면 모델은 단순 정정 대신 implicit recast

##### 3.3.16.7 우리 §3.3에 L5 추가 후 frame

| | Model 1 (1–2주차) | Model 2 (3–4주차) | Model 3 (5–8주차) |
|---|---|---|---|
| L1 (timbre) | CosyVoice 2 reference audio | CosyVoice 2 + per-speaker TTS LoRA | CosyVoice 2 + per-speaker TTS LoRA |
| L2 (prosody) | CosyVoice 2 instruction | CosyVoice 2 instruction | CosyVoice 2 instruction |
| L3 (lex-syn) | Style Card + system prompt | Style Card + system prompt | QLoRA (Qwen 3.6, Model 3) |
| L4 (discourse) | Style Card + system prompt | Style Card + system prompt | QLoRA (Qwen 3.6, Model 3) |
| **L5a (전략 패턴)** | **Style Card v1 + RAG** | **Style Card v1 + RAG** | **QLoRA with function-annotated dialogue data** |
| L5b (전략 competence) | RAG over ELF strategies | RAG over ELF strategies | RAG + QLoRA |
| L5c (co-construction) | Interaction design | Interaction design | Interaction design |

**해석:** Model 2에도 LoRA가 들어가지만 이것은 **per-speaker TTS LoRA**다. 따라서 음색·prosody·voice consistency만 바꾸고 Qwen의 text-level L5 전략은 Model 1과 동일하게 유지한다. Model 3에서 처음 **Qwen 3.6 text QLoRA**와 function-annotated dialogue data를 추가하므로, L5a/L5b의 text behavior가 바뀌는 단계는 Model 3이다. Model 2에 text LoRA를 추가하려면 별도의 대화 corpus와 새로운 실험 설계가 필요하며 현재 계획에는 포함하지 않는다.

→ **L5는 fine-tuning으로 fully 재현 불가능. RAG + Interaction design으로 보완. L5c는 시스템이 "tendency"만 가질 수 있고, 실제 co-construction은 학습자와 모델의 interaction에서 발생.**

## 9. 권고 아키텍처 재정의: text LLM + TTS + 3D NPC

### 9.1 Two-Stack Benchmark 전략 (PNU-style)

Qwen 3.6 text streaming는 low-latency audio-to-audio 대화와 카메라 입력에는 강점이 있다. 그러나 실제 화자의 clone voice, 수치로 고정된 말속도, 문장 내부 pause, word/phoneme timing 기반 lip-sync, 실제 발화 텍스트의 검증은 별도 제어가 필요한 문제다. 따라서 본 프로젝트는 **Native Live Stack**과 **Cascade Stack**을 병행 구현하여 비교한다.

*   **Native Live Stack:** `gemini-3.1-flash-live-preview` 기반 native audio-to-audio. 지연 시간이 낮으나 세밀한 발화 제어가 어려움.
*   **Cascade Stack:** `ASR → Text LLM → TTS` 분리형 구조. 발화 속도(rate)와 문장 내 휴지(SSML break)의 수치적 조작이 가능하여 연구 변인 통제에 유리.

이 분리형 구조를 기본으로 하며, 구현 코드에서 adapter interface로 분리하여 공급자를 바꾸어도 Unity/Unreal과 대화 정책은 유지된다.


### 9.2 실시간성: 가능한 방식과 금지할 방식

실시간 `text LLM → TTS`는 가능하다. 다만 token 하나가 도착할 때마다 읽게 하면 끊기고 억양이 망가진다. streaming LLM의 텍스트를 punctuation 또는 안전한 절 경계까지 짧게 buffer한 후 TTS로 보내고, 첫 chunk가 재생되는 동안 다음 chunk를 생성한다.

```text
LLM: “Maybe the first thing you could try is …”
→ buffer at clause boundary
→ TTS starts speaking that clause
→ LLM and TTS continue producing the next chunks in parallel
```

이 구조에서는 first-token latency, first-audio latency, chunk duration, queue length, interruption/cancel time, text/audio alignment를 기록한다. 사용자가 끼어들면 즉시 TTS playback을 중단하고, 아직 재생하지 않은 chunks를 폐기하며, 새 ASR turn으로 넘어간다.

### 9.3 Strict Log Schema 및 지연 시간 측정

상황별 말속도 변화와 상호작용 품질을 기록하기 위해 PNU 프로젝트의 엄격한 로그 스키마를 이식한다.

*   **필수 타임스탬프:** `user_turn_end_ts`, `first_model_event_ts`, `first_audio_out_ts`, `response_end_ts`, `interruption_detect_ts`, `playback_stop_ts`.
*   **지연 지표:**
    *   `response_onset_latency = first_audio_out_ts - user_turn_end_ts`
    *   `interruption_stop_latency = playback_stop_ts - interruption_detect_ts`
*   **구현 위치:** dialogue policy + LLM prompt/context 및 client playback/turn manager.

Cloud TTS/SSML을 통해 속도와 pause를 제어할 경우, 해당 control이 실제 출력에 반영되는지(fidelity)와 그에 따른 latency cost를 함께 기록한다.

### 9.4 언어스타일 corpus의 올바른 역할

문법 구조, discourse marker, filler, code-switching, 수리(repair) 방식은 voice clone이 아니라 LLM style controller의 대상이다. 대규모 원문을 매 turn prompt에 넣지 않는다.

```text
curated consented transcript/corpus
→ human review and annotation
→ speaker/style profile + small evidence bank
→ retrieval of only relevant, non-identifying examples
→ LLM response plan
→ final text → TTS
```

Style profile에는 자주 쓰는 discourse marker, 문장 길이, register, code-switching의 허용 위치, L1 transfer를 과장하지 않는 범위, repair/hesitation 관행을 기록한다. “Korean English”나 “Vietnamese English”는 단일한 목소리·문법·억양이 아니다. 특정 인물의 consented profile 또는 명시적으로 넓고 비본질화된 **voice class**로 정의하며, caricature/deficit framing을 금지한다.

### 9.5 세 가지 구현 경로 — commercial TTS/Vrew는 필수 아님

| 경로 | 구성 | 장점 | 제약/판단 |
|---|---|---|---|
| Google managed | Qwen 3.6 text-generation + Cloud TTS 또는 Cloud TTS + Unity/Unreal | API 통합과 속도/pause 제어가 비교적 단순 | Cloud TTS는 prebuilt voice 중심; 실제 특정 인물 clone은 별도 custom-voice eligibility/consent audit 필요 |

### 9.6 voice-cloning 원자료와 윤리 gate

가장 좋은 source는 NPC의 대상 화자를 **직접 섭외하여, 영어 발화가 포함된 별도 녹음과 사용 목적별 서면 동의를 받는 것**이다. 동의서는 적어도 다음을 분리한다.

1. 연구용 prototype 재생 여부
2. 외부 데모/발표에서의 사용 여부
3. 모델 학습·fine-tuning·reference-audio conditioning 중 어느 방식인지
4. 영어/다국어 합성 허용 여부
5. avatar와 결합한 사용, 온라인 배포, 2차 이용, 보관 기간, 철회·삭제 절차

공개 코퍼스의 각 화자는 대체로 특정 NPC의 정체성 복제를 허용한 것이 아니다. 따라서 공개 코퍼스의 직접적인 '개인 복제(Identity Cloning)' 사용 가능 여부는 현재 **사용자가 재확인 중**이다. 윤리적/법적 문제가 해결되기 전까지는 특정 개인을 닮게 하는 source audio로 사용하지 않으며, 특정 개인을 복제하지 않는 'Voice Class' 또는 'Style Transfer' 방식의 접근을 우선 검토한다. 또한 NPC가 실제 화자 본인과 실시간 대화하고 있다는 인상을 주지 않도록 항상 synthetic NPC/voice-replica임을 표시한다.

### 9.7 과거 L1-specific 자료 조사 메모 (현재 운영 경로에서 제외)

2026-08의 특정 L1 중심 후보 조사 기록은 현재 Global Englishes 화자군과 consented composite voice-class 설계로 대체한다. 해당 자료를 특정 개인의 clone source로 사용하지 않으며, 현재 Model 1–3의 학습·평가 입력으로 자동 편입하지 않는다. 필요한 corpus는 §9.10의 접근성·동의·라이선스 기준을 다시 확인한 뒤 별도 승인한다.

#### 9.9.1 Cascade용 transcript 저장 흐름

본 연구는 native audio stack 대신 **cascade**를 쓰므로 transcript 저장 트리거가 다르다.

- Native Live: `turnComplete` 이벤트 시 user/model transcription을 한 turn 단위로 저장

```
[학습자 음성] → [ASR chunk] → Apps Script save (LiveTranscript.user)
  → [LLM streaming chunk] → Apps Script save (LiveTranscript.model + chunk_index)

```

#### 9.10.0-A 대화자료 적합성 재분류 (2026-09-11)

**최우선 확정 source: ICNALE Spoken Dialogues**

현재 사용 가능성 검토 기준으로 ICNALE Spoken Dialogues를 Model 3의 최상위 대화자료로 배치한다. 이 corpus는 controlled learner interaction이지만 질문–응답, picture description, role-play, clarification, elaboration 및 reflection이 포함되어 있어 학생들의 lexical, syntactic, discourse, pragmatic features를 분석할 수 있다. 현재 프로젝트에서는 **ICNALE Spoken Dialogues를 우선 사용**하고, 다른 대화 corpus는 사용자가 접근 조건을 확인한 뒤 필요할 때만 추가한다.

L2-ARCTIC (TAMU)은 prompted/read speech가 중심이므로 Model 3 대화·text fine-tuning source로는 매우 제한적이다. 반면 MRPL2 (Zenodo)는 현재 접근 승인 전이라 실제 파일의 recording design을 확인하지 못했으므로 reading인지 conversation인지 단정하지 않는다. MRPL2는 우선 **자료 성격 미확인 보류 source**로 남기고, 파일과 documentation을 받은 뒤 재분류한다. MRPL2의 US·UK 자료가 포함되어 있다는 기존 표기는 삭제하며, US·UK reading 자료의 활용 가능성은 OpenSLR의 SLR45/SLR83에 별도로 귀속한다.

기존 inventory는 **음성·발음 분석 자료**와 **text LLM fine-tuning용 대화 자료**를 구분하지 않았다. 이 구분은 Model 1–3의 핵심 전제다. 문장을 읽은 자료는 voice/prosody/phonetic reference로는 유용하지만, 말투·turn-taking·syntax·lexis·pragmatics를 학습할 대화 corpus로 간주하지 않는다.

| 출처 | 실제 자료 성격 | Model 1 voice | Model 3 text/ELF | 판정 |
|---|---|---:|---:|---|
| **MRPL2 (Zenodo)** | 23명·14 L1 non-native English utterances, phonetic/mispronunciation annotation; **recording design not yet verified** | 보류(파일·documentation 수령 후 판정) | 미확인 | **현재는 자료 성격을 단정하지 않음** |
| **Speechocean762 (SLR101)** | Mandarin L1 화자의 pronunciation-assessment sentence recordings; 대화 아님 | 가능(voice class 제한) | 불충분 | **발음·평가만** |
| **L2-ARCTIC (TAMU)** | Main corpus: CMU ARCTIC prompted/read speech (~1 hour per speaker, ~1,132 short sentences); V5 also lists an un-scripted suitcase subset for 22/24 speakers, but no turn-based dialogue transcript | 가능(추가 허가 확인) | 불충분 | **read speech primary; suitcase supplementary only; no dialogue transcript** |
| **ELFA** | 약 131시간 academic ELF recordings/transcripts; dialogic/polylogic events 67%, audio restricted | 권리 승인 후 가능 | **강함** | **우선 신청** |
| **VOICE 3.0** | 1M words naturally occurring spoken ELF interactions; transcript 중심, raw audio 공개 여부 확인 필요 | 제한적 | **강함** | **ELF transcript 우선** |
| **ACE** | Asian spoken interactive ELF: meetings, panels, Q&A, conversations; 공개 transcript 중심 | 제한적 | **강함** | **Asian ELF 우선** |
| **ICNALE Spoken Dialogues** | 30–40분 oral interviews, picture descriptions, role plays, Q&A, clarification and reflection; audio/video link, controlled learner interaction | 가능(사용 조건 확인 완료) | **최상위** | **현재 Model 3 최우선 대화 source** |
| **COREFL** | spoken L2 English, transcript와 audio download 가능; 과제·응답 중심 | 가능(license 확인) | **중간** | **실용 후보** |
| **Speak & Improve Corpus 2025** | 약 315시간 spontaneous speaking-test recordings; 일부 manual transcript, 대화보다는 prompt response | 제한적 | 중간 | **보조 후보** |
| **LINDSEI** | informal learner interviews, transcript와 recording 연구자료; 표준 배포본 audio는 제한 | 제한적 | **중간** | **신청 후보** |
| **Trinity Lancaster Corpus** | 약 4.2M words candidate–examiner spoken L2 interaction; audio 공개 여부 불명확 | 제한적 | **강함** | **신청 후보** |

**핵심 결론:** 현재 다운로드한 SLR·TAMU 자료는 Model 3의 text LLM fine-tuning에 제한적이며, L2-ARCTIC은 참고용 voice/prosody 보조 자료로 분류한다. MRPL2는 아직 파일을 받지 못했으므로 reading/conversation 여부와 활용 범위를 보류한다. US·UK reading 자료의 활용 가능성은 MRPL2가 아니라 OpenSLR의 SLR45/SLR83에 해당한다. Model 3의 핵심은 사용 가능성이 확인된 ICNALE Spoken Dialogues이며, 실제 turn-based transcript와 학생 발화 맥락을 우선 활용한다.

**대화 corpus 우선순위:** (1) **ICNALE Spoken Dialogues — 현재 최우선·사용 가능 source**, (2) ELFA/VOICE/ACE의 자연 발생 ELF transcript, (3) COREFL의 audio-transcript matched spoken data, (4) TLC/LINDSEI/Speak & Improve의 접근권과 audio 조건 확인 순서다. Corpus transcript를 QLoRA에 바로 넣지 않고, 대화 turn과 pragmatic function을 먼저 annotation한다.

#### 9.10.0-B ICNALE Spoken Dialogues 영상 활용 계획

ICNALE Spoken Dialogues의 약 40–45분 semi-structured interview 영상은 Monologues보다 Model 3에 훨씬 적합하다. 인터뷰어와 학습자의 질문–응답, picture description, role-play, clarification, elaboration이 함께 있어 lexical·syntactic·discourse·pragmatic 분석이 가능하다. 다만 자연 발생 ELF 대화가 아니라 통제된 learner interview라는 점은 유지한다.

**두 사람 음성 처리:**

```text
video
→ audio extraction
→ speaker diarization
→ Student / Interviewer label
→ timestamp correction
→ student-only audio export + full dialogue transcript
```

mixed mono track이면 diarization 도구를 사용한 뒤 사람이 timestamp를 확인한다. 겹침 발화는 source separation으로 억지로 복원하지 않고 TTS 학습에서 제외한다. 인터뷰어 음성은 학생 TTS LoRA에서 제외하지만, 인터뷰어의 질문은 Qwen text/ELF 학습을 위한 대화 맥락으로 보존한다.

**학생 audio 검수 규칙:** 화자별 검수에서는 원본 시간축을 보존하는
`*_SPEAKER_01_TIMELINE.wav`를 원본 video/full mixed audio와 대조한다.
`TIMELINE.wav`는 학생 구간만 원래 시간 위치에 남기고 나머지를 무음으로
만든 candidate이므로, 시간 표시가 원본과 일치한다. 발화를 이어 붙인
`*_SPEAKER_01_CONCATENATED.wav`는 원본 timestamp가 보존되지 않으므로
잔여 인터뷰어 음성의 위치를 찾는 검수 기준으로 사용하지 않는다. 학생
발화 중 인터뷰어 음성이 겹쳐 들리면 해당 overlap 구간을 학생 TTS/reference
audio에서 제외한다. 1초 미만의 짧은 backchannel도 명확히 들리면 제외하며,
겹침으로 학생 발화가 잘린 경우에는 해당 segment 전체를 제외한다. 의심
구간은 KM Player에서 1초 단위로 대략적인 시간대만 기록해도 충분하고,
정제 시 앞뒤에 소폭의 여유를 둔다. 원본 video와 full dialogue transcript는
그대로 보존하고, 이 제외 규칙은 student-only TTS audio에만 적용한다.

**용도 분리:**

| 추출 자료 | 사용처 |
|---|---|
| 학생 audio + 학생 발화의 정확한 transcript | Model 2/3 per-speaker CosyVoice 2 TTS LoRA 후보 |
| 인터뷰어·학생 전체 turn-labelled transcript | Model 3 Qwen QLoRA/RAG의 dialogue·pragmatic-function 자료 |
| 인터뷰어 audio | TTS 학습에서 제외; 필요 시 diarization 품질 확인용 |
| 원본 video | 제한 저장; consent·license 범위 안에서만 보관·처리 |

학생 발화가 약 30분이고 음질이 실제로 양호하다면 **per-speaker TTS LoRA에는 충분히 유망**하다. 그러나 30분 전체를 그대로 넣지 않고, 겹침·clipping·심한 noise·긴 무음을 제거한 10–20분 clean segment를 우선 선별한다. 30분이라는 길이만으로 품질을 보장하지 않으며, read/controlled task의 한 명 발화로 국가나 English variety 전체를 대표하지 않는다.

반대로 Model 3 text fine-tuning에서는 학생만 추출하지 않는다. 학생 발화만 남기면 질문·응답 맥락과 repair 구조가 사라지므로, 전체 transcript를 보존하고 `speaker_role`, `turn_id`, `task`, `pragmatic_function`을 annotation한다. 학생 audio와 학생 transcript가 일치하는 쌍만 TTS 학습에 사용한다.

**ICNALE Spoken Dialogues region code:** `ENS`는 English Native Speakers, `MYS`는 Malaysia, `PAK`은 Pakistan이다. 현재 운영 분류는 `ENS` 1개, Expanding Circle의 CHN/TWN·JPN·IDN·THA·KOR, Outer Circle의 HKG·PHL·MYS·PAK로 정리할 수 있다. 이 Circle 분류는 분석을 위한 operational grouping이며 ICNALE의 learner metadata와 국가·L1·English variety를 동일시하지 않는다.

**최종 판정:** ICNALE Spoken Dialogues 영상은 Model 3의 핵심 대화자료 후보이며, 학생 audio는 Model 2/3의 TTS adapter 후보로 사용할 수 있다. 단, 영상·audio·TTS 출력 사용 허가를 별도로 확인하고, 실제 분리·전사 품질을 표본 검수한 뒤 채택한다.

#### 9.10.0-C 처리 분담과 참가자 identity provenance

**사용자가 모든 diarization을 직접 수행할 필요는 없다.** 원본 video 또는 mixed audio를 연구자 제한 저장소에 두면, 기술 측에서 audio extraction, speaker diarization, WhisperX word-level timestamp, forced alignment, student-only export를 수행할 수 있다. 사용자는 화자 라벨과 애매한 구간만 수동 검토한다. 겹침 발화는 source separation으로 무리하게 복원하지 않고 제외한다.

자료 전달 원칙은 용도별로 나눈다.

| 목적 | 필요한 자료 | 처리 |
|---|---|---|
| 학생 TTS LoRA | 학생만 포함한 audio + 그 audio의 정확한 transcript | 학생 audio만 사용 |
| Model 3 text/ELF | 인터뷰어와 학생의 전체 turn-labelled transcript | 양쪽 turn과 맥락 보존 |
| diarization 자동화 | 원본 video/mixed audio + 기존 transcript | 기술 측 분리 후 사용자 검수 |
| privacy 최소화 | 분리·검수 완료 후의 student audio | 원본 video는 제한 보관 |

따라서 최종적으로 기술 측에 필요한 핵심 입력은 **학생-only audio와 matching transcript**이며, Model 3 annotation을 위해서는 **인터뷰어·학생 양쪽이 표시된 전체 transcript**도 필요하다. 원본 mixed video는 분리가 필요한 경우에만 제한적으로 사용하고, 작업 후 보관·삭제 정책을 적용한다.

**참가자 identity 원칙:** chatbot에는 참가자별로 일관된 **synthetic participant persona**가 필요하지만, 실제 참가자의 누락된 개인정보를 사실처럼 복원하거나 만들어내면 안 된다. 다음 provenance 구분을 사용한다.

```yaml
participant_id: ICNALE_<region>_<code>
persona_identity: synthetic_composite_persona
observed_in_interview:
  - <직접 발화·영상·공식 metadata로 확인된 정보>
inferred_from_interview:
  - <낮은 확신의 해석; 모델 입력 전 사용자 승인>
unknown_or_withheld:
  - age
  - detailed English-learning history
  - family, residence, occupation, and other identifying facts
not_claimed: true
```

인터뷰에 실제로 드러난 정보는 `observed`로 기록하고, 합리적 추론은 `inferred`로 표시하며, 드러나지 않은 나이·영어 학습 이력·가족·거주지 등은 임의로 채우지 않는다. 챗봇에 필요한 배경은 실제 참가자의 biography가 아니라 **명시적으로 synthetic이라고 표시한 composite persona**로 설계한다. 이 persona는 일관된 이름·관심사·상호작용 목표를 가질 수 있지만, 특정 ICNALE 참가자의 실제 정체성이나 생애를 주장하지 않는다.

#### 9.10.0-G Model 1 speaker diarization 순서도

```text
FULL_STEREO/WAV 확인
  → pyannote speaker diarization
  → SPEAKER_00/01 segment CSV·RTTM 생성
  → video/transcript로 Student·Interviewer role 매핑
  → 애매한 구간 수동 검수
  → overlap/clipping 제거
  → Student-only audio + matching transcript export
  → full turn-labelled transcript 보존
```

현재 3개 pilot audio는 full mixed WAV와 stereo WAV까지 추출했으며, 실제 diarization은 `scripts/diarize_model1.py`로 실행한다. 격리된 `.venv-diarization`에 `pyannote.audio`를 설치했고, Windows TorchCodec가 요구하는 shared FFmpeg도 설치·확인했다. 자동 실행에 필요한 사용자 단계는 Hugging Face access token/model access이며, token을 코드나 history에 저장하지 않고 `HF_TOKEN` 환경변수로만 주입한다. `03_qc/diarization_review_template.csv`에서 diarized speaker를 Student/Interviewer로 확정한 뒤에만 `04_student_audio_pending`을 채운다. 역할 확정 후 학생 audio는 먼저 `*_SPEAKER_01_TIMELINE.wav`로 원본과 대조하고, 확인된 clean 구간만 `*_SPEAKER_01_CONCATENATED.wav` 또는 최종 student-only 파일로 사용한다.

학생 TTS에는 학생 audio와 matching transcript만 사용한다. Model 3 text/ELF에는 인터뷰어 질문을 포함한 전체 turn-labelled transcript를 사용한다. source separation은 overlap 구간의 보조 수단일 뿐이며, 분리 artifact가 생기면 해당 구간은 TTS 학습에서 제외한다.

#### 9.10.0-H CHN diarization 실행 기록

`ICNALE_SD_CHN_004_FULL_STEREO.wav`에 `pyannote/speaker-diarization-community-1`을 실행하여 RTTM과 segment CSV를 생성했다. CSV에는 583개 segment가 있으며 `SPEAKER_00` 214개(원시 합계 731.1초), `SPEAKER_01` 369개(원시 합계 1340.0초)로 기록되었다. 두 화자의 겹침 segment가 포함되므로 이 합계는 exclusive speaking time이 아니다. 0.5초 미만의 짧은 fragment가 191개 있어 overlap·boundary fragment를 수동 검수하고 정리해야 한다.

CHN 결과는 역할과 segment를 검수하여 확정했으며, 같은 pipeline을 IDN·JPN에 적용한다. 전체 583개 CHN segment를 모두 영상으로 재검수하는 대신, `03_Transcript`의 `[T]`/`[S]`를 기준표로 삼고 시작·중간·후반의 긴 구간과 화자 전환 구간을 표본 확인한다.

#### 9.10.0-I ICNALE SD 학습자 수준(CEFR) 반영

`01_Participants`의 `CEFR` metadata를 화자·대화 sampling에 포함한다. SD 학습자 405명은 `A2_0` 66명, `B1_1` 89명, `B1_2` 173명, `B2+` 77명이며, `ENS` 20명은 `N/A`다. KOR 20명을 포함한 현재 source pool에서 A2–B2+ 분포를 보존해 특정 proficiency에 편중되지 않도록 한다.

| CEFR code | 해석 | 현재 활용 |
|---|---|---|
| `A2_0` | lower proficiency learner | accommodation·clarification 사례 |
| `B1_1`, `B1_2` | intermediate learner bands | Model 3 dialogue/pragmatic sampling의 중심 |
| `B2+` | upper-intermediate/advanced band | elaboration·stance·complex repair 사례 |
| `N/A` (`ENS`) | native reference metadata | learner fine-tuning 대상이 아닌 비교 reference |

CEFR은 participant metadata이므로 transcript만으로 새로 추정하지 않는다. transcript에서는 CEFR별 lexical·syntactic·turn-taking·repair 양상을 질적으로 확인하고, Model 1 음성 profile이나 synthetic persona에 CEFR을 곧바로 화자 정체성·지능·문화적 특성으로 변환하지 않는다. Model 1에서는 응답 길이·어휘 난이도 조절에 참고하고, Model 3에서는 CEFR을 sampling/분석 stratification 변수로 사용한다.

#### 9.10.0-K 즉시 사용 가능한 자료와 provider 활용 경로 (2026-09-13)

아래 자료의 국가·지역 표기는 모집단 대표성 주장이 아니라 **의사소통 사례와 voice/strategy condition을 구분하기 위한 metadata**다. 개별 참가자나 corpus가 국가 전체의 영어를 대표한다고 해석하지 않는다. 자료가 부족한 화자군은 이미 접근 가능한 corpus 사례 또는 hosted synthetic voice로 보완하되, source 성격과 사용 목적을 분리해 기록한다.

| 자료/condition | 현재 활용 | 권장 기술 경로 | 제한 |
|---|---|---|---|
| `ICNALE_SD_CHN_004` clean student audio + matching transcript | Model 1 단일 기술 pilot | `Deepgram STT → Qwen 3.6 → CosyVoice 2 reference-audio TTS` 또는 기존 transcript로 STT 생략 | learner interview 사례; consent·license scope 확인 전 외부 공개/clone 금지 |
| SLR45 USA, SLR83 UK, SLR70 Nigeria | voice/prosody 사례와 hosted TTS 비교 baseline | audio는 `CosyVoice 2` reference/voice-class 조건으로만 검토; 텍스트는 필요한 경우 별도 분석 | read speech이면 turn-taking·ELF pragmatics 자료로 사용하지 않음; chatbot 출력·clone permission 확인 |
| Singapore·India·Philippines 관련 확보/신청 자료 | 부족한 화자군의 사례 보강 | 허가 후 audio+transcript를 분리해 voice/prosody 또는 text/ELF 용도로 사용 | corpus별 access, consent, TTS·fine-tuning·온라인 사용 조건을 개별 확인 |
| `Helsinki/ELFA_txt`, `ELFA_xml` 등 transcript 중심 자료 | Model 3의 ELF strategy/function RAG | 전체 원문을 매 turn 전송하지 않고 소규모 function-labelled retrieval로 사용 | audio가 없으면 TTS/reference source로 사용하지 않음 |
| Deepgram stock voices (American, British, Singaporean, Indian, Australian, Filipino 등) | 즉시 사용 가능한 synthetic TTS condition | Deepgram TTS 또는 Deepgram Voice Agent의 `speak` provider로 사용; `voice_id`·model·speed 기록 | 실제 국가/지역 화자 대표가 아니며, CosyVoice TTS LoRA 학습 source가 아님 |

**실행 경로는 직접 cascade를 primary로 하고 Voice Agent는 선택적 smoke test로 둔다.**

1. **Model 1–3 primary cascade:** `학생 mic → Deepgram STT → Qwen 3.6 system prompt/QLoRA + Style Card/RAG → CosyVoice 2/TTS LoRA → audio`. Model 1은 fine-tuning 없이 system prompt/RAG와 동의된 reference audio로 end-to-end를 검증하고, Model 2–3에서 TTS LoRA와 Qwen QLoRA를 순차적으로 추가한다.
2. **Optional hosted smoke test:** `학생 mic → Deepgram Voice Agent(STT + turn-taking + LLM + TTS) → audio`. 빠른 turn-taking·barge-in 확인에는 사용할 수 있지만, managed LLM/TTS를 쓰면 연구 Model 1–3 조건이 아니며 primary artifact·평가 결과에 혼합하지 않는다. corpus audio는 voice/prosody 사례, corpus transcript는 text/ELF strategy 자료로 분리한다.

따라서 Deepgram은 **standalone STT provider로 계속 사용**하고, TTS는 CosyVoice 2를 canonical로 유지하며 Deepgram TTS stock voice는 선택적 비교 조건으로만 사용한다. Model 1–3의 primary 경로는 `Deepgram STT → Qwen 3.6/QLoRA + Style Card/RAG → CosyVoice 2/TTS LoRA` 직접 cascade다. Deepgram Voice Agent는 필요할 때만 turn-taking·barge-in을 빠르게 확인하는 별도 smoke test로 둔다. 속도는 Qwen의 응답 길이·pause 지시와 TTS의 `speed` 설정으로 조절하고, provider/model/voice ID/speed와 실제 WPM·first-audio latency를 기록한다. 개인 AI용 본인 음성은 corpus 참가자 음성과 섞지 않고 별도 voice ID·Style Card·consent 범위로 관리한다.

## 10. LLM 발화 제어 (Prompt + DSP 하이브리드)

본 연구는 **fine-tuning 없이** 시스템 프롬프트와 클라이언트 DSP(재생 배속·pause 주입) 하이브리드로 LLM 발화 특성을 통제한다. 다음 두 레이어를 동시에 운용한다.

### 10.1 두 통제 레이어

| 통제 대상 | LLM 프롬프트 레이어 (확률적) | 클라이언트 DSP 레이어 (수치적) |
|---|---|---|
| 발화 속도(Speed) | 자연스러운 운율 — 천천히 말할 때 모음·호흡 강조 | 코드상 정확한 배속 (예: `playbackRate = 1.15`) |
| Pause | "1~2초 쉼을 두라" 같은 상황 인지형 지시 | SSML break 또는 클라이언트 무음 구간 고정 |
| 말투(register) | 다정함·친절함 등 감정선 표현 | (불가) |
| 재현성 | 매 호출마다 미세 변동 가능 | 호출 간 완전 동일 |
| 적응성 | 학습자 반응에 따라 동적 조절 가능 | 외부 trigger 없이는 정적 |

### 10.2 권장 기본값

- **기본 엔진**: 시스템 프롬프트 기반 제어 (자연스러움 우선)
- **보조**: 학습자가 복습 시 선호에 따라 0.8x / 1.0x / 1.2x를 고를 수 있는 UI 배속 슬라이더 (클라이언트 DSP)
- **Prompt + DSP 동시 사용**: 운율·감정은 prompt, 정확도 배속·pause는 DSP

### 10.3 SLA 기법 통합 (Pause, Recast, Repair)

본 연구의 LLM system prompt에는 다음 4가지 발화 규칙을 강제한다.

#### 10.3.1 Strategic Pause & Slowdown
- **적용 시점**: (1) 핵심 학술 용어를 처음 언급할 때, (2) 학습자가 머뭇거리거나 당황하는 음성 신호가 감지될 때
- **프롬프트 기법**: "학생이 어려워하거나 망설일 때는 발화 속도를 20% 늦추고, 문장 사이에 의도적으로 1~2초의 침묵(Pause)을 두어 학생이 스스로 생각할 인지적 여유를 제공하세요."

#### 10.3.2

**Recast (자연스러운 재진술)**
- **정의**: 학생 발화의 문법·어휘 오류를 직접 지적하지 않고, 올바른 형태를 문맥 속에서 자연스럽게 되받아쳐 모델링
- **효과**: 정의적 여과막(Affective Filter) 상승 방지
- **예시** (학습자 발화 → AI Recast):
  - Learner: "Yesterday I read many books at the library with my friends."
  - AI: "You read a lot of books at the library yesterday. Which one stood out to you?"

#### 10.3.3 Repair (자기 수정 유도)
- **정의**: 정답을 바로 주지 않고 학습자가 스스로 발화를 수정하도록 유도(Elicitation)
- **기법**: 의도적 pause + 유도 질문
- **예시**:
  - 학습자: "a learner statement containing an unspecified hesitation"
  - AI (1.5-second pause): "There was a gas that plants absorb through their leaves. Which gas was it?"

#### 10.3.4 Encouragement (짧고 명확한 격려)
- 학습자가 정답/좋은 생각을 말했을 때 진심 어린 칭찬을 짧고 명확하게 건넴
- 과도한 칭찬/칭찬 inflation 금지

### 10.4 권장 System Prompt 골격 (Cascade용)

```
You are a Global Englishes interlocutor engaging a learner from your assigned Global Englishes context.

[발화 규칙]
- 1~2문장으로 짧게 끊고, 즉시 학습자 반응을 기다리라.
- 새로운 개념/핵심 표현 도입 시 발화 속도 25% 감속, 문장 끝에 1~2초 pause.
- 절대 급하게 말하지 말 것.

[상호작용 규칙]
- Recast: 학습자 오류는 직접 지적하지 말고 올바른 형태로 자연스럽게 되받아쳐 모델링.
- Repair: 학습자가 망설일 때 바로 답을 주지 말고 유도 질문으로 자기 수정 유도.
- Encouragement: 학습자가 진전을 보이면 짧고 명확하게 격려. 과도한 칭찬 금지.

[Turn 관리]
- 학습자 발화가 끝나면 즉시 반응하되, 짧은 청취 확인 후 응답 시작.
- 학습자가 끼어들면 즉시 발화 중단.
```

### 10.5 DSP 측 구현 메모

- **입력 audio chunking**: 16kHz 기준 100ms = 1,600 샘플 단위로 WebSocket 전송 (네트워크·직렬화 부담 90% 감소)
- **재생**: `playbackRate` 슬라이더 (0.8x–1.2x)
- **Barge-in**: 클라이언트 VAD로 TTS 재생 중단, 큐 초기화
- **Cascade STT 후보**: Deepgram Nova-2 또는 Whisper Realtime (지연 150–300ms)

## 11. 메모리·로그 정책

### 11.1 Model 1–3 memory grid

메모리는 DDR 단계별 모델 상태를 분리해 관리한다. 동일 참가자의 이전 단계 응답을 다음 단계에 자동으로 섞지 않는다.

| 모델 | 정의 | DDR 역할 |
|---|---|---|
| **Model 1** | Qwen 3.6 system-prompt-conditioned + Style Card/RAG | 1–2주차 음성 baseline |
| **Model 2** | Model 1 + per-speaker CosyVoice 2 TTS LoRA | 3–4주차 음색 강화 |
| **Model 3** | Qwen 3.6 QLoRA + Model 2 TTS LoRA + ELF strategy RAG | 5–8주차 화용 전략 통합 |

Qwen 3.8은 Model 3의 9–10주차 비교 변형으로만 관리한다. 3D avatar memory와 camera memory는 3주차 이후 별도 namespace로 추가한다.

### 11.4 Log schema (Cascade 강제)

PNU-style strict timestamp schema를 cascade용으로 적용:

| 필드 | 정의 | 측정 대상 |
|---|---|---|
| `user_turn_end_ts` | ASR final transcript 시점 | latency 시작점 |
| `first_model_event_ts` | LLM 첫 chunk 시점 | TTFT |
| `first_audio_out_ts` | TTS 첫 PCM chunk 재생 시점 | response_onset_latency |
| `response_end_ts` | LLM 마지막 chunk 시점 | turn duration |
| `interruption_detect_ts` | client VAD가 학습자 발화 감지 시점 | barge-in |
| `playback_stop_ts` | TTS 재생 중단 시점 | interruption_stop_latency |

**지표**:
- `response_onset_latency = first_audio_out_ts - user_turn_end_ts`
- `interruption_stop_latency = playback_stop_ts - interruption_detect_ts`
- `chunk_duration`, `queue_length`, `text_audio_alignment`

### 11.5 version 관리

모든 manifest에 다음을 기록:
- `prompt_version`: LLM system prompt 변경 시 bump

- `voice_id`: clone voice 변경 시 bump (6화자군 swap 시)
- `corpus_profile_version`: corpus feature DB schema 변경 시 bump (Model 3에서 특히 중요)

### 주제 1: Multi-human discussion + camera integration

**연구 질문**: 여러 명의 인간과의 토론에도 참여할 수 있는가? 카메라까지 달아주면?

**핵심 도전**:
- **Polylogue turn-taking**: 다자 대화에서 누가 발언할지 결정 (Kaur 2011, Pitzl 2016)
- **Camera-based multimodal input**: 비언어적 단서 (gaze, gesture, facial expression) 인식
- **Speaker identification & attention allocation**: 카메라 영상으로 발언자 식별 + 관심 배분
- **Multi-party repair sequences**: 다자 간 misunderstandings 해결 전략

**기술적 요구사항**:
- Multimodal LLM with video input (Gemma 4 27B with vision, 또는 Qwen 3.8 + video encoder (3주차 이후))
- Real-time camera feed processing (WebRTC)
- Speaker diarization + gaze detection (OpenPose, MediaPipe)
- Polylogue turn-taking algorithm (VAD + visual attention)

**연구 설계**:
- 3-4명 학습자 그룹 + ELF 아바타
- Camera로 전체 그룹 촬영 (upper body + face)
- 전사 + CA 분석: multi-party repair sequences, topic negotiation, accommodation strategies

**인용**: Kaur (2011), Pitzl (2016), Mauranen (2012/2018), Cogo & Dewey (2012)

**연구 질문**: Translanguaging을 구사하는 multimodal, multilingual 챗봇을 구현할 수 있는가?

**핵심 개념**:
- **Translanguaging** (García & Wei 2014): 단순 code-switching/code-mixing이 아님. 언어 경계를 넘나드는 유동적 의사소통.
- **Semiotic resources** (Kress 2010): 언어뿐만 아니라 gesture, image, object, space, relationship 등 모든 의미 생성 수단.
- **Content-based teaching**: 언어교육뿐만 아니라 특정 과목(content) 교육에도 활용 (Creese & Blackledge 2010).

**기술적 요구사항**:
- **Multimodal input**: text + speech + image + video + gesture (camera)
- **Multilingual LLM**: 모든 언어를 단일 repertoires로 처리 (code-switching이 아닌 fluid translanguaging)
- **Gesture generation**: 비언어적 semiotic resources 생성 (3D avatar gesture)
- **Context-aware resource selection**: 상황·관계·내용에 따라 적절한 semiotic resources 동원

**연구 설계**:
- 학습자가 특정 과목 내용 (예: 과학, 역사)을 ELF 아바타와 함께 학습
- Camera로 학습자의 gesture, facial expression, 주변 환경 인식
- 아바타가 언어 + gesture + image를 유동적으로 조합하여 설명
- 전사 + multimodal CA 분석: semiotic resources의 유동적 동원 과정

**인용**: García & Wei (2014), Kress (2010), Creese & Blackledge (2010), Smit (2010)

### Controlled pronunciation/acoustic comparison: Singapore recording set and CMU ARCTIC prompts

The Singapore recording set currently under review contains the same or closely matching controlled prompts as the CMU ARCTIC prompt set, including `arctic_a0001`, “Author of the danger trail, Philip Steels, etc.” This prompt must be identified as **CMU ARCTIC-derived**, not as a Harvard/IEEE sentence and not as naturally occurring Singapore conversation. The final corpus name, speaker metadata, and license must be checked against the downloaded provider documentation before publication.

This set will be used in the paper only as a **controlled pronunciation and acoustic comparison resource**:

- identical or controlled text reduces lexical-content differences between speakers;
- word/phoneme alignment supports segmental pronunciation, intelligibility, and ASR comparison;
- duration, pause, F0, intensity, spectral and voice-quality measures support prosodic/acoustic comparison;
- the material may provide a controlled reference for Model 1 voice-quality evaluation.

The prompt list itself is not a pronunciation test and does not provide an official score. Any pronunciation result must state the separate alignment, ASR, phoneme-error, intelligibility, or acoustic measurement procedure. Because the recordings are prompted/read speech, they must not be used as evidence of conversational style, turn-taking, ELF pragmatics, or Model 3 dialogue behaviour.

Some prompts have a spoken-like or colloquial register rather than exclusively formal written prose. This increases their value as controlled examples of spoken-register pronunciation, rhythm, and prosody, but it does not supply interactional pragmatics. The dataset will therefore be labelled **controlled read speech with spoken-like register variation**, not conversational speech.

**Required paper wording:** the Methods/Data section must explicitly report that the Singapore set was used as controlled read-speech material for pronunciation/acoustic comparison, identify the prompts as CMU ARCTIC-derived where confirmed, state that it was not used as conversational dialogue data, and include the provider’s required citation/attribution and access date. The paper must not describe this set as a natural Singapore English conversation corpus.

Because the complete Singapore collection is approximately 2 TB, the project will not download or process it exhaustively. Only a small, documented subset of speakers will be selected for Model 1 pronunciation/acoustic comparison and possible reference-audio testing. Selection will be based on consent/license scope, speaker metadata, audio quality, prompt coverage, and relevance to the comparison design. The report and paper must state the subset size, speaker IDs or anonymized IDs, access date, and selection criteria.

**Reference to verify and cite:** Kominek and Black, *The CMU Arctic Speech Databases*, Speech Synthesis Workshop 2004, https://www.cs.cmu.edu/~awb/papers/ssw5/arctic.pdf. The Singapore provider’s own dataset documentation and license take precedence for the final dataset name and attribution.

## Canonical Model 1 persona registry (2026-09-13)

Model 1 now has one dependency-free JSON boundary between voice data and the
application. `PersonaRegistry` loads a registry mapping stable `persona_id`
values to profile filenames, and resolves a `PersonaProfile` containing
`voice_id`, display metadata, source-grounded facts, explicitly fictionalized
display identity, conversation behaviour, and prompt context. Invalid or
unknown IDs fail with `ValueError`; profile and registry representations do
not include mapping contents, secrets, or audio bytes.

### Files and data boundary

```text
voices/personas/
├── registry.json
└── icnale_chn_004_student.json
services/model1/
└── personas.py
```

`registry.json` is intentionally source-neutral: each entry is only
`persona_id -> profile filename`, so ICNALE is not a required schema for
future corpus, licensed recording, or synthetic composite sources. Profile
files keep these top-level sections separate:

- `source_grounded`: facts and relative provenance paths supported by the
  repository;
- `fictionalized`: display-only identity fields, with the preferred name
  explicitly marked fictional;
- `behavior`: interaction guidance, not a claim about the source participant;
- `prompt_context`: the small mapping sent to Qwen, without raw audio.

The initial `icnale_chn_004_student` profile uses display label `CHN-004` and
a fictional preferred name. It records the ICNALE source ID, confirmed
`SPEAKER_01` student role, clean-audio processing status, and provenance files.
Consent and permitted-use scope remain **pending**; no profile field converts
that pending review into a rights claim, and no accent marker or stereotype is
inferred.

### Application usage

```python
from pathlib import Path
from services.model1 import Model1Cascade, PersonaRegistry

registry = PersonaRegistry(Path("voices/personas/registry.json"))
cascade = Model1Cascade.from_config(config, persona_registry=registry)
result = cascade.run_persona(
    "icnale_chn_004_student",
    {"task": "short greeting"},
    audio_bytes,
)
```

`run(...)` remains the explicit voice-ID API. `run_persona(...)` resolves the
voice ID and passes only `prompt_context` to Qwen under a clearly labelled
`Persona Profile` system-prompt section.
